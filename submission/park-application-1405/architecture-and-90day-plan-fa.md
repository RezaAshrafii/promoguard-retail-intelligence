# معماری MVP و برنامه اعتبارسنجی ۹۰ روزه

## معماری فعلی

```text
CSV فروش و پروموشن
        |
کنترل کیفیت و قرارداد داده
        |
پنل هفتگی فروشگاه × کالا
        |
baseline فقط از تاریخچه پیش از رویداد
        |
ممیزی observational + interval + warningها
        |
JSON قابل ممیزی
        +-------------------+
        |                   |
     FastAPI         داشبورد فارسی Streamlit
```

### چرا این معماری مهم است؟

هسته تحلیل از رابط جداست. یعنی CLI، API و داشبورد از یک منطق استفاده می‌کنند و عددها در سه محل
جداگانه محاسبه نمی‌شوند. قبل از تحلیل، سیستم داده‌های ناقص، تاریخ نامعتبر، فروش منفی، پرچم
پروموشن نامعتبر و دانه‌بندی تکراری را بلوکه می‌کند.

### وضعیت کنونی

- قابلیت موجود: پردازش پنل عمومی واقعی، endpointهای API، dashboard، گزارش JSON و تست.
- قابلیت برنامه‌ریزی‌شده: اتصال امن به داده شریک، آزمایش کنترل‌شده، causal benchmark، monitoring
  و production storage.
- مرز علمی: خروجی فعلی observational است؛ causal effect یا profit قطعی را شناسایی نمی‌کند.

## برنامه ۹۰ روزه

### روز ۱ تا ۳۰ — کشف مسئله و آمادگی داده

هدف: ثابت کنیم مسئله برای یک شریک واقعی مهم است و داده لازم وجود دارد.

- ۵ تا ۱۰ مصاحبه ساختاریافته با مسئول trade marketing، داده یا فروش؛
- انتخاب یک شریک pilot و امضای توافق دسترسی محدود به داده؛
- inventory از ستون‌های موجود، کیفیت و شکاف داده؛
- تعیین KPIهای مشترک: زمان تهیه گزارش، completeness داده، نرخ استفاده از insight و طراحی آزمون؛
- خروجی تصمیم: ادامه pilot فقط اگر داده و مسئله برای هر دو طرف قابل تایید باشد.

### روز ۳۱ تا ۶۰ — pilot محدود و طراحی آزمایش

هدف: یک مورد استفاده کم‌ریسک را با معیار از پیش نوشته‌شده اجرا کنیم.

- انتخاب یک دسته کالا و تعداد محدود فروشگاه؛
- ایجاد data contract و pipeline تکرارپذیر؛
- طراحی گروه کنترل/holdout یا آزمایش تصادفی با تأیید شریک؛
- ثبت margin، موجودی، قیمت، تقویم و رخدادهای مخدوش‌کننده در صورت دسترسی؛
- بازبینی انسانی قبل از هر اقدام؛ محصول هیچ کمپینی را خودکار اجرا نمی‌کند.

### روز ۶۱ تا ۹۰ — ارزیابی و تصمیم ادامه

هدف: نه «موفق نشان دادن ایده»، بلکه تصمیم گرفتن بر پایه evidence.

- ارزیابی کیفیت داده و پایداری pipeline؛
- مقایسه نتایج observational با نتیجه آزمایش کنترل‌شده، در صورت امکان؛
- اندازه‌گیری زمان گزارش‌گیری، وضوح تصمیم برای کاربر و نرخ پذیرش؛
- ثبت failure caseها و محدودیت‌ها؛
- تصمیم مشترک: ادامه به محصول، اصلاح مسئله، یا توقف.

## معیارهای موفقیت پیشنهادی

این‌ها هدف‌های pilot هستند، نه نتیجه موجود:

| معیار | تعریف | معیار تصمیم |
|---|---|---|
| صحت داده | درصد رکوردهای عبورکرده از قرارداد | آستانه با شریک تعیین می‌شود |
| تکرارپذیری | امکان تولید گزارش با همان ورودی | ۱۰۰٪ در runهای کنترل‌شده |
| قابلیت استفاده | زمان رسیدن از داده به گزارش | با baseline فرآیند فعلی شریک مقایسه می‌شود |
| اعتبار تصمیم | تطبیق با آزمایش یا review انسانی | از پیش تعریف می‌شود |
| پذیرش | بازخورد کاربران pilot | مصاحبه و ثبت رفتار استفاده |

## درخواست مشخص از پارک

1. معرفی منتور product/retail؛
2. اتصال به یک یا دو شریک بالقوه برای discovery و pilot؛
3. فضای کاری و شبکه تخصصی؛
4. بازبینی مسیر حقوقی و privacy پیش از ورود داده واقعی.

ما درخواست تأیید درآمد، مقیاس‌پذیری یا اثر اقتصادی پیش از اجرای pilot نداریم.
