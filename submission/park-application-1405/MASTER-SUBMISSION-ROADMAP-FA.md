## ۱. هدف نهایی

یک پرونده کوتاه، صادقانه و قابل ممیزی ساخته شود که داور در دو دقیقه بتواند پاسخ این شش سؤال را
بگیرد:

1. مسئله دقیق چیست و چه کسی آن را دارد؟
2. چه چیزی واقعاً ساخته شده است؟
3. چرا این راه‌حل با گزارش BI معمولی فرق دارد؟
4. چه شاهدی برای توان اجرای بنیان‌گذار وجود دارد؟
5. چه چیزهایی هنوز اثبات نشده‌اند؟
6. پارک دقیقاً چگونه می‌تواند احتمال موفقیت pilot را بالا ببرد؟

## ۲. تعریف نسخه موفق پرونده

پرونده وقتی آماده ارسال است که همه شروط زیر هم‌زمان برقرار باشند:

- فرم رسمی با اطلاعات واقعی، تاریخ و امضا تکمیل شده باشد؛
- شرایط احراز دانشگاه متقاضی تلفنی یا کتبی تأیید شده باشد؛
- کارت ملی و گواهی اشتغال به تحصیل آماده ولی خارج از Git باشند؛
- یک PDF یک‌صفحه‌ای و یک ضمیمه شواهد حداکثر چهارصفحه‌ای وجود داشته باشد؛
- ویدیوی ۱۱۰ تا ۱۱۸ ثانیه‌ای از demo واقعی بدون login باز شود؛
- GitHub روی یک tag/release نهایی، README روشن و تست سبز قرار داشته باشد؛
- عدد نسخه، تعداد تست، تعداد ردیف و نتیجه audit در همه خروجی‌ها یکسان باشد؛
- هر ادعای مهم به کد، artifact، مصاحبه واقعی یا برچسب «فرضیه» وصل باشد؛
- هیچ داده شخصی، credential، داده raw یا ادعای مشتری/درآمد غیرواقعی در مخزن نباشد.

## ۴. راهبرد ارائه

### جمله جایگاه‌یابی

> PromoGuard سامانه ممیزی شواهد پروموشن خرده‌فروشی است که قبل از توصیه، کیفیت داده، baseline،
> عدم‌قطعیت و هشدارهای تصمیم را کنار هم می‌گذارد و در صورت ناکافی‌بودن شواهد، آزمایش کنترل‌شده
> پیشنهاد می‌دهد.

### مخاطب اولیه

تیم داده، فروش یا trade marketing یک خرده‌فروشی/برند FMCG که داده فروش و تقویم پروموشن دارد،
اما برای تفکیک «افزایش مشاهده‌شده» از «شاهد کافی برای تصمیم» فرآیند قابل ممیزی ندارد.

### جایگزین‌های واقعی

| جایگزین | مزیت جایگزین | شکاف مورد هدف PromoGuard |
|---|---|---|
| Excel و تحلیل دستی | در دسترس و انعطاف‌پذیر | تکرارپذیری، کنترل leakage و هشدار ثابت ضعیف است |
| داشبورد BI | گزارش سریع KPI | کیفیت استنتاج و عدم‌قطعیت را الزاماً ممیزی نمی‌کند |
| تحلیل موردی تیم داده | قابل سفارشی‌سازی | زمان‌بر و وابسته به analyst؛ استاندارد خروجی ثابت نیست |
| ابزار promotion خارجی | بلوغ محصول | داده، اتصال، هزینه و سازگاری محلی باید بررسی شود |
| PromoGuard | evidence-first و قابل ممیزی | هنوز pilot ایرانی، integration و اثر تجاری اثبات نشده است |

### درخواست دقیق از پارک

1. معرفی یک منتور retail/FMCG یا trade marketing؛
2. اتصال به یک شریک داده برای discovery و pilot محدود ۹۰روزه؛
3. بازبینی privacy، قرارداد داده و مدل همکاری pilot؛
4. کمک به تکمیل تیم فقط پس از روشن‌شدن نیاز واقعی نقش‌ها.

## ۸. پرسش‌های احتمالی داور و پاسخ کوتاه

### چرا این فقط یک داشبورد نیست؟

داشبورد KPI را نمایش می‌دهد؛ PromoGuard قبل از نتیجه‌گیری، قرارداد داده، baseline زمانی، عدم‌قطعیت
و هشدارهای اعتبار تصمیم را اجرا می‌کند و در کمبود شواهد از توصیه قطعی خودداری می‌کند.

### مشتری دارید؟

خیر؛ MVP روی داده عمومی واقعی ساخته شده است. هدف درخواست از پارک، دسترسی به discovery و partner
pilot برای اعتبارسنجی مسئله و اثر در محیط واقعی است.

### چرا خودت برای این کار مناسب هستی؟

دانشجوی آمار هستم و حساسیت پروژه به استنتاج اشتباه را به معماری تبدیل کرده‌ام: داده خراب متوقف
می‌شود، آینده وارد baseline نمی‌شود، interval و limitation در خروجی اجباری است و کد با تست و
artifact قابل بررسی ارائه شده است.

### تیم تک‌نفره ریسک نیست؟

هست و پنهان نشده است. فاز فعلی با یک بنیان‌گذار فنی قابل اجراست؛ بعد از discovery مشخص می‌شود
اولویت جذب، domain expert retail است یا data/product engineer. عضو صوری برای کامل‌کردن فرم اضافه
نمی‌شود.

### AI کجای محصول است؟

نسخه فعلی عمداً deterministic و قابل ممیزی است. مدل‌های پیچیده و LLM فقط وقتی اضافه می‌شوند که
خروجی عددی منبع حقیقت باقی بماند و ارزیابی hallucination وجود داشته باشد. ارزش MVP وابسته به API
مدل سوم‌شخص نیست.
