# گام ۸.۳.۵ — تثبیت محصول پیش از توسعهٔ بعدی

تاریخ اجرا: ۱۲ اکتبر ۲۰۲۶. این مرحله قابلیت تحلیلی تازه نمی‌سازد؛ مسیرهای موجود را قابل‌اعتمادتر می‌کند. فاز ۸ هنوز فعال است. مدل جاری همین جلسه استفاده شد؛ بازبینی مستقل با مدل دوم انجام نشده است.

## ۱. ورود داده؛ یک فایل نباید در دو بخش دو معنی داشته باشد

پیش از اصلاح، ممکن بود فایل در کنترل کیفیت پذیرفته شود اما تحلیل به‌خاطر فاصلهٔ اضافی نام ستون متوقف شود. خواندن CSV و استانداردسازی نام ستون‌ها مشترک شد. ` store_id ` همان `store_id` است، اما اگر هر دو نام در فایل باشند، سیستم آن‌ها را بی‌سروصدا ادغام نمی‌کند و برخورد ستون‌ها را گزارش می‌کند.

شناسه‌ها عدد محاسباتی نیستند: فروشگاه `001` نباید به `1` تبدیل شود. خوانندهٔ فایل، نام خام ستون شناسه را شناسایی می‌کند و آن را از ابتدا رشته می‌خواند؛ سپس فاصلهٔ نام ستون حذف می‌شود.

موجودی سه حالت دارد: مقدار معتبر غیرمنفی؛ مقدار خالی/نامعلوم؛ مقدار نامعتبر مثل متن، منفی یا بی‌نهایت. حالت سوم پیش از تحلیل رد می‌شود. حالت دوم به صفر تبدیل نمی‌شود؛ نبود اطلاعات با تمام‌شدن موجودی فرق دارد. اگر یک هفته موجودی نامعلوم و هفتهٔ دیگری صفر باشد، هر دو محدودیت جدا گزارش می‌شوند.

فایل‌های مرتبط: `src/promoguard/data/panel.py`، `src/promoguard/insights/promotion_audit.py`، `apps/api/contracts.py` و مسیرهای خواندن فایل در `apps/api/main.py`.

## ۲. چرخهٔ گزارش؛ هر تحلیل باید در صفحهٔ خودش باز شود

گزارش فروشگاهی نمودار روند دارد؛ گزارش آزمایش ایمیلی ساختار دیگری دارد. قبلاً تاریخچه می‌توانست گزارش ایمیلی را به صفحهٔ فروشگاهی بفرستد و برنامه سراغ نموداری برود که وجود ندارد. اکنون نوع تحلیل مسیر را تعیین می‌کند. برای گزارش‌های قدیمی، نام benchmark نیز کمک می‌کند نوع تشخیص داده شود. لینک قدیمی که به صفحهٔ اشتباه برسد، به صفحهٔ درست هدایت می‌شود.

تلاش مجددِ آزمایش دیگر مسیر ساخت گزارش فروشگاهی را صدا نمی‌زند. معیار، آستانه و فرض‌های مالی از گزارش قبلی بازیابی می‌شوند و شناسهٔ تازه ساخته می‌شود؛ گزارش قبلی بازنویسی نمی‌شود. اگر تنظیمات قبلی خراب یا مفقود باشد، API خطای روشن ۴۲۲ می‌دهد. گزارش موفق قابل تلاش مجددِ شکست نیست؛ ساخت تحلیل تازه مسیر مستقل خودش را دارد.

فایل‌های مرتبط: `frontend/app/report-view.mjs`، تعریف نوع همراه آن، صفحات اصلی و experiments، و `apps/api/main.py`. در صفحهٔ آزمایش، پاسخ درخواست قدیمی نمی‌تواند نتیجهٔ درخواست جدیدتر را جایگزین کند.

## ۳. پیام مدیریتی؛ رشد با رسیدن به هدف یکی نیست

فرض کن اثر درآمد حدود ۰٫۷۷ دلار به‌ازای هر نفر است، اما بازهٔ عدم‌قطعیت تقریباً ۰٫۴۲ تا ۱٫۱۲ دلار است. چون کل بازه بالاتر از صفر است، شواهد افزایش داریم. ولی اگر مدیر حداقل ۰٫۵ دلار بخواهد، بازه از دو طرف هدف عبور می‌کند؛ پس رسیدن به هدف هنوز روشن نیست. هدف ۹۹ دلار نیز با این بازه پشتیبانی نمی‌شود. یک عدد مثبت نباید خودکار به «کمپین موفق بود» تبدیل شود.

عنوان صفحه، تعداد نمونه و متن مقایسه از نتیجهٔ گزارش می‌آیند. انتخاب نرخ خرید یا بازدید دیگر متن ثابتِ افزایش درآمد یا نتیجهٔ ثابتِ مقایسهٔ دو نسخه را نمایش نمی‌دهد. مقایسهٔ مستقیم دو نسخه هدف تجاریِ در برابر کنترل ندارد و همین موضوع صریح نوشته می‌شود.

قواعد نمایش در `report-view.mjs` و برچسب‌های PDF در `src/promoguard/experiments/presentation.py` هستند. دو محیط اجرای متفاوت داریم، پس همسانی آن‌ها با تست کنترل شده است؛ قرار نیست جاوااسکریپت محاسبهٔ آماری پایتون را دوباره انجام دهد.

## ۴. بازتولید و PDF

باز کردن گزارش، پیامد، هدف، درصد حاشیه، هزینه‌های دو نسخه و توضیح منبع را در فرم برمی‌گرداند. هزینهٔ صفر معتبر است و نباید به مقدار پیش‌فرض دیگری تبدیل شود. خالی‌بودن فرض‌های مالی هم حفظ می‌شود.

بخش «تنظیمات این گزارش» به نتیجهٔ ذخیره‌شده مربوط است. تغییر فرم برای اجرای بعدی، گزارش قبلی یا PDF آن را تغییر نمی‌دهد. PDF نسخهٔ ۶ هدف و وضعیت هدف هر مقایسه را ثبت می‌کند. نوشتن PDF اتمیک است تا خواننده فایل نیمه‌نوشته نگیرد. نسخهٔ کش نتیجهٔ آزمایش به ۱.۴.۱ و فروشگاهی به ۲.۳.۰ تغییر کرده تا نتایج قبل از اصلاح دوباره استفاده نشوند. گزارش‌های قدیمی حذف نشده‌اند.

دو گزارش واقعی روی همان فایل عمومی ۶۴هزارنفری ساخته شدند:

- `rpt_44fc591ffe4f49a5`: هدف ۰٫۵ دلار؛ رسیدن هر دو نسخه به هدف هنوز روشن نیست.
- `rpt_304d2339cb444277`: هدف ۹۹ دلار؛ هیچ‌یک از دو نسخه به هدف تعریف‌شده پشتیبانی نمی‌شوند.

هر دو به ready رسیدند. PDFها هدف‌های متفاوت و متن متفاوت دارند. هر دو صفحهٔ PDF اول رندر و از نظر بریدگی، هم‌پوشانی و خوانایی بررسی شدند. گزارش قدیمی `rpt_8d86876df7644bfd` همچنان آماده و قابل بازیابی است.

## ۵. تست‌های جلوگیری از برگشت خطا

تست ورودی متن/منفی/بی‌نهایت موجودی را رد می‌کند؛ خالی و فاصله را صفر نمی‌گیرد؛ هشدار موجودی نامعلوم و صفر را جدا می‌سنجد؛ و فاصلهٔ نام ستون و صفر ابتدای شناسه را تا تحلیل کنترل می‌کند. تست API بازیابی تنظیمات تلاش مجدد، ورودی خراب و اتصال آپلود به گزارش را می‌سنجد. تست PDF هدف و برچسب واقعی هر گزارش را کنترل می‌کند.

تست‌های منطق فرانت مسیر، متن پویا، تفاوت هدف و جهت، و بازیابی مالی را بررسی می‌کنند. پنج تست Chromium روی build تولیدی، تاریخچه، لینک قدیمی، بازیابی معیار و هدف، لینک PDF، هزینهٔ صفر و تلاش مجدد را از رابط می‌آزمایند. پاسخ‌های ساختگی این تست‌ها فقط ابزار آزمون رفتار هستند؛ شاهد موفقیت تجاری محسوب نمی‌شوند. جداگانه یک مرورگر به API واقعی محلی وصل شد: هدف ۰٫۵ برگشت، وضعیت‌ها درست بودند و خطای صفحه ثبت نشد.

### نتیجهٔ اجرای نهایی

| کنترل | نتیجه |
|---|---|
| کل pytest | ۲۷۹ پاس؛ یک هشدار deprecation موجود |
| پوشش تست پایتون | ۸۰٫۷۴٪؛ بالاتر از حداقل ۷۰٪ |
| Bandit روی src و apps | پاس |
| تست منطق Node | ۱۳ پاس |
| تست مرورگر Playwright | ۵ پاس |
| Ruff و compileall | پاس |
| ESLint غیرتعاملی و TypeScript | پاس |
| build تولیدی Next | پاس |
| npm audit، کل وابستگی‌ها | صفر آسیب‌پذیری شناخته‌شده در زمان اجرا |
| git diff --check | پاس؛ فقط هشدار تبدیل LF/CRLF |

فرانت نیز به CI اضافه شد: نصب قطعی از lockfile، lint، تست، typecheck، build، نصب Chromium و تست مرورگر. هنوز پوش نشده و اجرای CI روی گیتهاب ادعا نمی‌شود. Python محلی ۳.۱۳ و Node محلی ۲۴ بود؛ CI برای Python ۳.۱۱ و Node ۲۲ تنظیم شده و برابری محیط‌ها هنوز روی runner تأیید نشده است.

اجرای پوشش تست ایراد اتصال SQLite را آشکار کرد: context manager تراکنش را commit یا rollback می‌کند اما اتصال را نمی‌بندد. در `apps/api/storage.py` بسته‌شدن قطعی اتصال پس از هر دو مسیر اضافه شد. دو تست در `tests/unit/test_storage_lifecycle.py` بسته‌شدن اتصال و rollback نوشتن ناموفق بدون تخریب رکورد قبلی را کنترل می‌کنند. هشدارهای اتصال باز پس از اصلاح در اجرای نهایی حذف شدند. ابزار پوشش و Bandit در محیط موقت `tmp/stabilization-qa` نصب شدند؛ محیط Python عمومی تغییر نکرد و این محیط در گیت نادیده گرفته می‌شود.

## ۶. bootstrap و ابزار توسعه

برای گروه کوچک‌تر از حداقل موجود، وضعیت هدف bootstrap اکنون «نمونه ناکافی» است، نه «هدف تعیین نشده». فرمول، بذر، تعداد تکرار و روش اصلی Welch تغییر نکردند. bootstrap از همان داده استفاده می‌کند و شاهد مستقل نیست.

lint بدون سؤال تعاملی اجرا می‌شود و قواعد جاوااسکریپت، تایپ‌اسکریپت و hooks را کنترل می‌کند. Next به ۱۵.۵.۲۷ و چند وابستگی آسیب‌پذیر به نسخهٔ اصلاح‌شده ارتقا یافتند. هشدار نبود افزونهٔ اختصاصی Next در ESLint باقی است؛ lint فعلی فعال است ولی ادعای پوشش قواعد اختصاصی Next نمی‌کنیم. هشدار deprecation ابزار ESLint ۹ و Starlette/httpx نیز به معنی شکست تست نیست، اما باید در نگهداری بعدی بررسی شوند. audit صفر، تضمین امنیت کامل نیست.

## محدودیت‌ها و نقطهٔ توقف

این مرحله سود واقعی شرکت یا اثربخشی تخفیف فروشگاهی را اثبات نمی‌کند. Hillstrom آزمایش ایمیلی عمومی است؛ هزینه و حاشیهٔ واقعی ندارد. فرض مالی واردشده همچنان مشارکت مشروط می‌سازد، نه سود تأییدشده. ورود کاربران/سازمان‌ها و استقرار عمومی در این مرحله ساخته نشده است؛ سرویس‌ها فقط روی loopback اجرا شده‌اند.

نسخهٔ فعلی محلی آمادهٔ بازبینی تثبیت است؛ قابلیت تازه اضافه نشده، کامیت و پوش انجام نشده و بازبینی مستقل مدل دوم هم انجام نشده است. برای ادامه، اول همین تغییرات را بازبینی و سپس با درخواست صریح منتشر می‌کنیم؛ بعد سراغ گام بعدی رودمپ می‌رویم.

## دستورهای تکرار

از ریشهٔ پروژه:

```powershell
$env:PYTHONPATH='src'
C:\Python313\python.exe -m pytest -q
C:\Python313\python.exe -m ruff check .
C:\Python313\python.exe -m compileall -q src apps demo
git diff --check
```

از پوشهٔ frontend:

```powershell
npm run lint
npm test
npm run typecheck
npm run build
npx playwright install chromium
npm run test:e2e
npm audit
```

تغییرات فرانت علاوه بر صفحات در package.json، lockfile، eslint.config.mjs، playwright.config.ts و e2e/report-lifecycle.spec.ts ثبت شده‌اند. workflow فرانت در `.github/workflows/ci.yml` است و خروجی‌های موقت Playwright در `.gitignore` کنار گذاشته شده‌اند. در صفحهٔ optimization فقط formatter استفاده‌نشده حذف شده؛ محاسبات آن تغییر نکرده‌اند.
