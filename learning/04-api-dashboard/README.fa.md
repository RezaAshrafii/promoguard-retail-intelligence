# فاز ۴ — API تایپ‌شده، داشبورد و دموی واقعی

## خلاصه خیلی ساده

تا پایان فاز ۳، پروژه می‌توانست داده را آماده کند، baseline بسازد و یک پروموشن را با کد یا CLI
ممیزی کند. مشکل این بود که داور پارک، مصاحبه‌کننده یا مدیر محصول برای دیدن نتیجه باید ساختار کد را
می‌شناخت. در فاز ۴ یک «در ورودی امن» و یک «ویترین قابل‌فهم» ساختیم:

- FastAPI در ورودی بررسی می‌کند درخواست و داده قابل قبول هستند؛
- Streamlit مراحل را به زبان فارسی و قدم‌به‌قدم نمایش می‌دهد؛
- موتور تحلیلی قبلی محاسبه را انجام می‌دهد؛
- گزارش JSON اجازه می‌دهد هر عدد بعداً ممیزی و بازتولید شود.

نکته مهم: رابط کاربری و API هیچ فرمول آماری تازه‌ای ندارند. این دو فقط با موتور اصلی صحبت
می‌کنند. بنابراین اگر فردا داشبورد عوض شود، منطق آماری دو نسخه متفاوت پیدا نمی‌کند.

## هدف کسب‌وکاری فاز

هدف این فاز پاسخ به این سؤال بود: «آیا یک داور غیرتوسعه‌دهنده می‌تواند پروژه را اجرا کند، داده را
ببیند، یک پروموشن را انتخاب کند و محدودیت نتیجه را بفهمد؟»

خروجی هنوز نرم‌افزار enterprise و هنوز اثبات اثر علّی نیست. این یک MVP قابل ارائه است که نشان
می‌دهد سه مهارت را هم‌زمان داریم: مهندسی داده، مدل‌سازی صادقانه و تبدیل تحلیل به محصول.

## مدل استفاده‌شده و دلیل انتخاب

- مدل اصلی: `gpt-5.6-sol`
- reasoning: `high`
- دلیل: طراحی قرارداد API، کنترل مرزهای ورودی و جلوگیری از دو نسخه شدن محاسبات، تصمیم‌های
  معماری مهمی بودند؛ اما estimator آماری فاز ۳ در این فاز تغییر نکرد.

در بازبینی داشبورد نیازی به تغییر مدل نبود. اجرای واقعی در مرورگر دو هشدار Streamlit را آشکار
کرد و همان‌جا اصلاح شدند؛ پس کیفیت از تست، اجرای واقعی و log به دست آمد، نه صرفاً از قوی‌تر کردن
مدل.

## معماری فاز ۴

```text
کاربر یا داور
    |
    +---- درخواست HTTP ----> FastAPI + Pydantic
    |                            |
    |                            +--> load/validate canonical panel
    |                            +--> promotion audit domain service
    |
    +---- تعامل تصویری ----> Streamlit فارسی
                                 |
                                 +--> همان load/validate
                                 +--> همان promotion audit domain service

منبع حقیقت محاسبات = src/promoguard
API و Dashboard = adapter، نه موتور تحلیل
```

این الگو را modular monolith می‌نامیم. برای یک پروژه تک‌نفره از microservice منطقی‌تر است، چون
استقرار و تست ساده می‌ماند ولی مرزها مشخص هستند.

## مرحله ۱ — قرارداد پنل استاندارد

فایل اصلی: `src/promoguard/data/panel.py`

این ماژول سه کار انجام می‌دهد:

1. اگر مسیر یک پوشه باشد، فایل `weekly_panel.csv` را در آن پیدا می‌کند؛ اگر مسیر خود CSV باشد،
   همان را می‌خواند.
2. در صورت نیاز سقف حجم فایل را قبل از بارگذاری کنترل می‌کند.
3. یک quality report ثابت می‌سازد.

حداقل ستون‌های ضروری:

- `week_end_date`: تاریخ پایان هفته؛
- `store_id`: شناسه فروشگاه؛
- `upc`: شناسه کالا؛
- `units`: تعداد فروش؛
- `promotion_flag`: صفر یا یک بودن پروموشن.

کنترل‌های کیفیت برنامه:

- خالی نبودن پنل؛
- وجود ستون‌های ضروری؛
- معتبر بودن تاریخ؛
- نداشتن ردیف تکراری در دانه‌بندی هفته × فروشگاه × کالا؛
- خالی یا منفی نبودن units؛
- صفر یا یک بودن promotion flag؛
- بیشتر نبودن تعداد ردیف‌ها از یک میلیون.

گزارش فقط `valid=true/false` نیست. تعداد ردیف، سری، ردیف پروموشن، بازه زمانی و تعداد هر نوع خطا
را نیز برمی‌گرداند تا کاربر بفهمد چرا داده رد شده است.

## مرحله ۲ — قراردادهای Pydantic

فایل اصلی: `apps/api/contracts.py`

Pydantic مانند نگهبان جلوی API است. قبل از رسیدن درخواست به منطق تحلیل، نوع و کامل بودن فیلدها
را بررسی می‌کند.

مثال مهم: برای انتخاب دستی رویداد باید `store_id`، `upc` و `start_date` هر سه با هم ارسال شوند.
ارسال فقط یکی از آن‌ها مبهم است و با خطای ۴۲۲ رد می‌شود. اگر هیچ‌کدام ارسال نشود، سیستم مطابق
قاعده از پیش مستندشده یک رویداد نماینده انتخاب می‌کند.

`contribution_assumption` اختیاری است و در صورت ارسال باید مقدار، کد ارز سه‌حرفی و منبع فرض را
داشته باشد. نبودنش به معنی صفر فرض کردن اثر مالی نیست؛ سیستم صادقانه می‌گوید اقتصاد کامل پروموشن
قابل محاسبه نیست. وجودش نیز recommendation را تغییر نمی‌دهد.

## مرحله ۳ — endpointهای FastAPI

فایل اصلی: `apps/api/main.py`

endpointها:

| مسیر | کار ساده آن |
|---|---|
| `GET /health` | نشان می‌دهد سرویس بالا است |
| `POST /v1/panels/validate` | پنل محلی را می‌خواند و اعتبارسنجی می‌کند |
| `POST /v1/panels/validate-upload` | فایل CSV آپلودی را با سقف حجم بررسی می‌کند |
| `POST /v1/promotions` | دوره‌های پروموشن را پیدا می‌کند |
| `POST /v1/audits` | یک رویداد مشخص یا نماینده را ممیزی می‌کند |

رفتار خطاها عمداً روشن است:

- فایل محلی پیدا نشود: ۴۰۴؛
- CSV خراب باشد: ۴۰۰؛
- پنل از نظر قراردادی نامعتبر باشد: ۴۲۲؛
- آپلود خالی باشد: ۴۰۰؛
- آپلود از ۱۲۰ MiB بیشتر باشد: ۴۱۳؛
- ترکیب فیلدهای درخواست غلط باشد: ۴۲۲.

سقف ۱۲۰ MiB کمی بالاتر از فایل واقعی تقریباً ۱۰۵ MB انتخاب شد. سقف یک میلیون ردیف نیز پنل
۵۲۴٬۹۵۰ ردیفی پروژه را می‌پذیرد ولی جلوی مصرف کنترل‌نشده حافظه را می‌گیرد. این محدودیت‌ها
تنظیمات کاربردی MVP هستند و معنای آماری ندارند.

FastAPI از همین قراردادها OpenAPI می‌سازد. پس داور می‌تواند در `/docs` schema ورودی و خروجی را
ببیند و endpoint را آزمایش کند.

## مرحله ۴ — داشبورد فارسی Streamlit

فایل اصلی: `apps/dashboard/app.py`

جریان کاربر:

1. منبع داده را انتخاب می‌کند: پنل واقعی پروژه یا CSV استاندارد؛
2. دکمه بارگذاری و کنترل کیفیت را می‌زند؛
3. آمار پنل و خطاها را می‌بیند؛
4. اگر داده معتبر باشد، دوره‌های پروموشن شناسایی می‌شوند؛
5. سیستم رویداد نماینده فاز ۳ را به‌صورت پیش‌فرض انتخاب می‌کند؛
6. کاربر در صورت داشتن یک فرض تأییدشده می‌تواند contribution sensitivity را همراه ارز و منبع وارد کند؛
7. ممیزی اجرا و مشاهده‌شده، مبنا، تفاوت، بازه‌ها و هشدارها نمایش داده می‌شود؛
8. نتیجه کامل به شکل JSON دانلود می‌شود.

برای سرعت رابط، بارگذاری دیتای محلی و شناسایی رویدادها cache می‌شود. در لیست کشویی حداکثر ۵۰۰
رویداد اول به‌علاوه رویداد نماینده نمایش داده می‌شود؛ ولی موتور تحلیل روی کل پنل واقعی کار می‌کند.

در بالای صفحه و کنار خروجی گفته می‌شود که نتیجه observational است و اثر علّی شناسایی نشده. این
متن یک تزئین نیست؛ بخشی از guardrail محصول است.

## مرحله ۵ — تست‌ها

فایل‌ها:

- `tests/unit/test_panel.py`
- `tests/integration/test_api.py`

تست واحد پنل موارد معتبر، ستون غایب، فروش منفی، flag نامعتبر، دانه تکراری، سقف ردیف، پیدا کردن
فایل در پوشه و مسیر گم‌شده را بررسی می‌کند.

تست integration با یک fixture کوچک و قطعی، مسیرهای HTTP را بررسی می‌کند: validation، فهرست
پروموشن، audit، نبود فایل، event key ناقص، آپلود معتبر، schema ناقص، فایل خالی و فایل بزرگ‌تر از
سقف. fixture تست «داده محصول» نیست و برای ادعای نتیجه استفاده نمی‌شود؛ فقط رفتار نرم‌افزار را
قابل‌تکرار می‌کند. دموی محصول جداگانه روی داده واقعی اجرا شده است.

نتیجه نهایی این فاز: ۴۷ تست پاس شد.

## مرحله ۷ — بازبینی واقعی مرورگر

داشبورد به‌صورت headless اجرا و در مرورگر محلی بررسی شد. مسیر زیر واقعاً کلیک و مشاهده شد:

```text
صفحه اصلی -> بارگذاری پنل -> کیفیت معتبر -> انتخاب رویداد نماینده
-> اجرای ممیزی -> نمایش تصمیم، عددها، هشدارها و دانلود JSON
```

بازبینی اول دو warning سمت سرور نشان داد:

1. `use_container_width` در نسخه جدید Streamlit منسوخ شده بود؛ با `width="stretch"` جایگزین شد.
2. جدول کنترل کیفیت در یک ستون string، integer و boolean مخلوط داشت؛ مقادیر نمایشی به string
   تبدیل شدند تا Arrow بدون fallback آن را serialize کند.

بعد از اصلاح، مسیر کامل دوباره اجرا شد و log سرور بدون warning یا error بود. این مثال خوبی برای
مصاحبه است: تست خودکار لازم است، اما رفتار واقعی رابط نیز باید مشاهده شود.

## توضیح ۳۰ ثانیه‌ای برای مصاحبه

«من یک MVP تحلیل پروموشن ساختم که روی پنل واقعی عمومی حدود ۵۲۵ هزار ردیفی اجرا می‌شود. هسته
تحلیل از API و داشبورد جداست تا محاسبات چند نسخه نشوند. FastAPI با schema تایپ‌شده ورودی معیوب،
فایل خالی و فایل بزرگ را رد می‌کند. داشبورد فارسی quality report، انتخاب رویداد، interval و
هشدارهای ادعای علّی را نشان می‌دهد. مسیر کامل با integration test، smoke test داده واقعی و
بازبینی مرورگر اعتبارسنجی شده؛ خروجی نیز JSON قابل ممیزی است.»

## سؤال‌های احتمالی مصاحبه و پاسخ کوتاه

### چرا FastAPI؟

چون type hint و Pydantic را مستقیم به validation و OpenAPI تبدیل می‌کند و برای سرویس تحلیلی
Python انتخاب ساده و قابل تستی است.

### چرا محاسبه را در endpoint ننوشتی؟

برای جلوگیری از duplicated business logic. CLI، API و dashboard باید یک نتیجه واحد تولید کنند.

### فرق validation upload با تحلیل چیست؟

validation باید حتی داده نامعتبر را به شکل گزارش نشان دهد؛ تحلیل فقط بعد از `valid=true` اجرا
می‌شود.

### چرا ۴۲۲؟

درخواست از نظر HTTP قابل خواندن است، ولی schema یا معنای ورودی برای پردازش قابل قبول نیست.

### چرا از microservice استفاده نکردی؟

برای MVP تک‌نفره هزینه عملیاتی اضافه می‌کرد. modular monolith مرزها را نگه می‌دارد و بعداً امکان
جدا کردن سرویس سنگین را می‌دهد.

### آیا داشبورد causal lift نشان می‌دهد؟

خیر. عدد تفاوت observed و baseline را با interval و عبارت صریح «causal effect not identified»
نشان می‌دهد.

### بزرگ‌ترین بهبود production چیست؟

ذخیره پنل در موتور تحلیلی مثل DuckDB/PostgreSQL، cache کنترل‌شده، authentication، rate limit،
job queue برای تحلیل سنگین و monitoring زمان/حافظه/خطا.

## تمرین برای تسلط صددرصدی

1. API را اجرا کن و در `/docs` هر endpoint را یک بار صدا بزن.
2. یک کپی کوچک CSV بساز، ستون units را حذف کن و ببین quality report چگونه آن را رد می‌کند.
3. فقط `store_id` را برای audit بفرست و خطای قرارداد را توضیح بده.
4. در داشبورد رویداد پیش‌فرض را اجرا و چهار warning واقعی را نام ببر.
5. فایل `promotion_audit.py` را پیدا کن و ثابت کن هیچ formula در `apps/` تکرار نشده است.
6. JSON خروجی را باز کن و برای هر عدد، فیلد متناظر در UI را پیدا کن.
7. محدودیت observational را بدون استفاده از کلمه‌های تخصصی برای یک مدیر محصول توضیح بده.

## فاز بعد چه می‌کند؟
