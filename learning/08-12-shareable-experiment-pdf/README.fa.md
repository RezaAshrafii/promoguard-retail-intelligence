# آموزش مرحلهٔ ۸.۳.۳ — گزارش PDF قابل دریافت برای آزمایش کمپین

## هدف این گام

قبلاً نتیجه فقط داخل داشبورد دیده می‌شد و دکمهٔ PDF برای آزمایش Hillstrom به مسیر export ممیزی فروشگاهی می‌رفت؛ یعنی از نظر نوع گزارش، خروجی درستی نبود. این گام مسیر PDF جداگانه‌ای برای آزمایش اضافه می‌کند و خروجی قابل نگهداری/ارسال می‌سازد.

## PDF چه چیزهایی دارد؟

- شناسهٔ گزارش، نوع آزمایش، شمار کل افراد و شمار هر یک از سه گروه؛
- پیامد اصلی و بازهٔ زمانی اندازه‌گیری؛
- هر سه مقایسهٔ ازپیش‌تعیین‌شده و بازهٔ هم‌زمان ۹۵٪؛
- میانگین پیامد برای گروه‌ها؛
- در صورت وجود ورودی مالی: حاشیهٔ مشترک، اختلاف هزینه و مشارکت محاسباتی مشروط برای هر مقایسه، همراه یادداشت منبعی که کاربر وارد کرده؛
- روش آماری، hash فایل، وضعیت مجوز منبع و محدودیت‌های تفسیر؛
- شمارهٔ صفحه و شناسهٔ گزارش در پاصفحه.

PDF اگر ورودی مالی نداشته باشد، به‌جای محاسبهٔ پولی می‌گوید فقط درآمد ناخالص اندازه‌گیری شده و سود/مشارکت خالص قابل محاسبه نیست. هیچ‌کدام از این دو حالت به معنای تأیید سودآوری یا پیشنهاد اجرای کمپین نیست.

## از کجا آن را دریافت کنیم؟

در صفحهٔ «ارزیابی با گروه کنترل»، پس از آماده‌شدن گزارش، دکمهٔ «دریافت گزارش PDF» ظاهر می‌شود. API همان شناسهٔ گزارش را می‌گیرد و اگر وضعیت هنوز `ready` نباشد، با خطای 409 اجازهٔ دریافت نمی‌دهد. آدرس فنی مسیر موجود این است:

```text
GET /v1/reports/{report_id}/pdf
```

سرور نوع گزارش را تشخیص می‌دهد: گزارش randomized experiment با قالب آزمایش صادر می‌شود و گزارش ممیزی هفتگی/فروشگاهی همچنان از قالب قبلی استفاده می‌کند. فایل PDF در cache محلی گزارش ذخیره می‌شود؛ محاسبهٔ آماری دوباره اجرا نمی‌شود.

## نکته‌های فنی مهم

- فونت محلی Vazirmatn و شکل‌دهی متن فارسی استفاده می‌شود؛ گزارش وابسته به دانلود فونت از اینترنت نیست.
- ورودی‌های متنی، به‌خصوص منبع مالی واردشده توسط کاربر، پیش از قرارگرفتن در Paragraph از نظر نشانه‌های HTML escape می‌شوند تا متن شبیه markup باعث خرابی یا ساخت محتوای ناخواسته نشود.
- پول‌ها به‌صورت LTR و با `USD` نوشته می‌شوند. مقدار منفی با پرانتز نمایش داده می‌شود تا علامت منفی در متن راست‌به‌چپ جابه‌جا نشود.
- PDF فقط نتیجهٔ ذخیره‌شده را قالب‌بندی می‌کند؛ estimator، آزمون آماری، بازهٔ اطمینان یا وضعیت نتیجه تغییر نکرده‌اند.
- فایل عمومی Hillstrom مجوز بازتوزیع صریح در صفحهٔ ناشر ندارد؛ PDF hash و هشدار مجوز را نشان می‌دهد، اما دادهٔ خام را داخل فایل یا repository قرار نمی‌دهد.

## فایل‌های تغییرکرده

- `apps/api/pdf.py`: سازندهٔ PDF مخصوص randomized experiment، جدول‌های فارسی، فرمت پول LTR، escape ورودی، شناسه و شمارهٔ صفحه.
- `apps/api/main.py`: انتخاب قالب export بر پایهٔ `analysis_type` در مسیر PDF مشترک؛ مسیر قبلی حفظ شده است.
- `frontend/app/experiments/page.tsx` و `frontend/app/globals.css`: لینک دریافت PDF فقط برای گزارشی که آماده شده.
- `tests/unit/test_experiment_pdf.py`: بررسی ساختار PDF، شناسه، اعداد مهم، قالب منفی و ساخت PDF با ورودی متنی شامل علامت‌های markup.
- `tests/integration/test_api.py`: مسیر API برای report آماده، ذخیرهٔ cache و رد report در حال اجرا.
- `ROADMAP.md`: ثبت برش و وضعیت فاز.

## چطور خروجی را سخت‌گیرانه بررسی می‌کنیم؟

1. تست واحد PDF محتوای کلیدی و قابل استخراج مثل شناسه و اعداد LTR را کنترل می‌کند. متن فارسی با حروف presentation-shaped در PDF نگهداری می‌شود؛ پس برای فهم درست آن، صرفاً جست‌وجوی رشتهٔ خام در خروجی `pypdf` کافی نیست.
2. تست API کنترل می‌کند report آماده فایل PDF می‌دهد و report ناآماده فایل نمی‌دهد.
3. PDF واقعی به PNG تبدیل و تمام صفحات از نظر کنتراست، بریدگی، به‌هم‌ریختگی RTL، علائم منفی و شکست صفحه بازبینی می‌شوند.
4. تست‌های کامل مخزن و build/typecheck فرانت‌اند اجرا می‌شوند.

## مرز و ادامه

این گزارش برای benchmark عمومی است و ارزش ارائهٔ روش/محصول را دارد، اما مدرکِ سودآوری شرکت ایرانی نیست. اعداد مالیِ تستی باید در PDF هم با «فرض» و منبع تستی دیده شوند. بعد از این گام، کار روش‌شناختی مهم‌تر **bootstrap و سنجش پایداری بازه‌ها** است؛ سپس فقط چند زیرگروه ازپیش‌تعیین‌شده و با کنترل خطر مقایسه‌های متعدد. دریافت و بازبینی دادهٔ مجاز شریک همچنان شرط تبدیل این benchmark به شواهد مشتری واقعی است.
