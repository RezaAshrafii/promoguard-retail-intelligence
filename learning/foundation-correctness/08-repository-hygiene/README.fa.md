# بخش ۸: پاک‌سازی مخزن، License و metadata

## مشکل چه بود؟

در ریشه پروژه یک `docker-compose.yml` برای PostgreSQL وجود داشت، ولی هیچ مسیر اجرایی برنامه از آن
استفاده نمی‌کرد. همچنین پوشه‌هایی مثل `causal` و `optimization` فقط یک فایل توضیحی خالی داشتند.
این ظاهر می‌توانست داور را به اشتباه بیندازد که زیرساخت یا مدل‌هایی ساخته شده‌اند که واقعاً وجود
ندارند. به این حالت «infrastructure theater» می‌گوییم: نمایش ابزار بدون مسئله و مسیر اجرایی واقعی.

## چه تغییر کرد؟

- PostgreSQL بلااستفاده و placeholder انبار داده حذف شد.
- packageهای خالی causal، cannibalization، features، optimization و uncertainty حذف شدند.
- برنامهٔ آینده آن‌ها در `ROADMAP.md` باقی ماند؛ پس ایده حذف نشده، فقط ادعای پیاده‌سازی حذف شده است.
- `LICENSE` با Apache-2.0 اضافه شد.
- `pyproject.toml` به License و آدرس رسمی repository متصل شد.
- `docs/repository-metadata.md` متن Description و Topicهای بدون اغراق را ثبت کرد.
- `DATA_SOURCES.md` روشن کرد که License کد، مجوز datasetها نیست.
- ADR 0007 دلیل انتخاب مجوز و گزینه‌های جایگزین را ثبت کرد.

## Apache-2.0 خیلی ساده یعنی چه؟

دیگران می‌توانند کد شما را ببینند، تغییر دهند و حتی تجاری استفاده کنند، به شرط رعایت notice و شرایط
مجوز. این مجوز درباره فایل داده dunnhumby هیچ حقی نمی‌دهد؛ چون شما صاحب آن dataset نیستید و اصلاً
آن را داخل Git نگذاشته‌اید.

## چرا حذف پوشه خالی بهتر از نگه‌داشتن آن است؟

معماری حرفه‌ای فهرست آرزوها نیست. هر component باید ورودی، خروجی، تست و مصرف‌کننده واقعی داشته
باشد. وقتی Phase 6 یا 7 شروع شود، module مربوطه همراه با contract و تست برمی‌گردد؛ آن زمان وجودش
معنا دارد.

## چیزی که در مصاحبه باید بگویید

«من عمداً PostgreSQL و packageهای خالی را حذف کردم چون MVP فعلی local و file-based است. persistence
را وقتی اضافه می‌کنم که ingestion تکرارشونده، migration و integration test واقعی داشته باشم. این
کار scope را کوچک نکرد؛ فاصله ادعا تا واقعیت را صفر کرد.»

## روش بررسی

پس از حذف، کل importها جست‌وجو می‌شوند، Ruff و pytest اجرا می‌شوند و package build metadata کنترل
می‌شود. اگر runtime dependency پنهانی وجود داشته باشد، این gate اجازه commit نهایی نمی‌دهد.
