# اصلاح پایه ۵: پوشش واقعی مقایسه دو مدل

وضعیت: تکمیل‌شده

تاریخ: ۳۱ اوت ۲۰۲۶ / ۹ شهریور ۱۴۰۵

مدل بازبینی معماری: `gpt-5.6-sol` با reasoning سطح `xhigh`

## مسئله به زبان ساده

برای اینکه دو مدل forecast منصفانه مقایسه شوند، باید هر دو برای یک ردیف یکسان prediction داشته
باشند. اگر مدل فصلی مقدار سال قبل را پیدا نکند ولی مدل naive مقدار داشته باشد، استفاده از آن ردیف
فقط برای یکی از مدل‌ها مقایسه را ناعادلانه می‌کند.

نسخه قبلی درست عمل می‌کرد و فقط ردیف‌های paired را امتیاز می‌داد، اما گزارش فقط دو عدد می‌گفت:

```text
ردیف paired: 41,516
ردیف حذف‌شده: 16,615
```

مشکل این بود که نسبت پوشش، علت حذف و پراکندگی حذف بین foldها معلوم نبود. بنابراین خواننده نمی‌دانست
نتیجه مقایسه روی چند درصد داده تست بنا شده است.

## اصلاح معماری

تابع `_paired_eligibility_summary` برای هر fold این موارد را محاسبه می‌کند:

- تعداد همه ردیف‌های non-promotion تست؛
- تعداد ردیف‌هایی که هر دو prediction را دارند؛
- نسبت پوشش paired؛
- تعداد ردیف حذف‌شده؛
- علت حذف در سه گروه بدون هم‌پوشانی.

علت‌ها:

1. `missing_seasonal_only`: مدل فصلی تاریخ دقیق lag را ندارد، ولی naive قابل محاسبه است؛
2. `missing_naive_only`: مدل فصلی موجود است، ولی naive موجود نیست؛
3. `missing_both_predictions`: هیچ‌کدام prediction ندارند.

همین حسابداری برای کل backtest نیز جمع می‌شود. مجموع سه علت باید دقیقاً برابر تعداد حذف‌ها باشد؛
پس هیچ ردیفی بی‌توضیح باقی نمی‌ماند و هیچ ردیفی دو بار شمرده نمی‌شود.

## مثال خیلی ساده

فرض کن دو کالا در fold تست داریم:

```text
کالای A: seasonal دارد، naive دارد  -> paired
کالای B: seasonal ندارد، naive دارد -> حذف با علت missing_seasonal_only
```

در این حالت:

```text
non-promotion rows = 2
paired rows = 1
coverage = 1 / 2 = 50%
excluded = 1
```

تست جدید دقیقاً این وضعیت را می‌سازد و انتظار دارد coverage برابر `0.5` باشد.

## چه چیزی تغییر نکرد؟

- prediction هیچ مدلی تغییر نکرد؛
- WAPE، MASE، bias و interval coverage به‌خاطر این اصلاح تغییر نمی‌کنند؛
- تعریف paired comparison تغییر نکرد؛
- هیچ ردیف جدیدی وارد metric نشده است؛
- این تغییر فقط شفافیت و قابلیت ممیزی گزارش را بالا می‌برد.

## فایل‌های تغییرکرده

- `src/promoguard/forecasting/evaluation.py`: حسابداری coverage کل و per-fold؛
- `tests/unit/test_forecasting.py`: تست نسبت پوشش و علت حذف؛
- `docs/evaluation-protocol.md`: قرارداد گزارش‌دهی؛
- `reports/phase-02/forecast-evaluation.json`: artifact واقعی بازتولیدشده؛
- `reports/phase-02/forecast-eligibility.csv`: جدول پوشش و علت حذف در هر fold؛
- این فایل: توضیح فارسی تصمیم و نتیجه.

## خروجی داده واقعی

گزارش واقعی دوباره با این command ساخته شد:

```powershell
python -m promoguard.cli forecast-evaluate `
  --input data/processed/breakfast-at-the-frat `
  --output reports/phase-02
```

نتیجه:

| شاخص | مقدار |
|---|---:|
| ردیف non-promotion در پنجره‌های تست | 58,131 |
| ردیف paired | 41,516 |
| پوشش paired | 71.42% |
| کل ردیف حذف‌شده | 16,615 |
| فقط seasonal مفقود | 16,563 |
| فقط naive مفقود | 0 |
| هر دو prediction مفقود | 52 |

پوشش foldها بین 65.05% و 78.36% بود. علت غالب حذف، در دسترس نبودن lag دقیق ۵۲هفته‌ای برای مدل
فصلی بود. این نتیجه مهم است: metric مقایسه معتبر و paired است، ولی فقط روی 71.42% ردیف‌های
non-promotion تست قابل تعمیم مستقیم است. این محدودیت اکنون پنهان نیست.

## سؤال مصاحبه‌ای

### چرا metric را روی تمام ردیف‌های تست نگرفتی؟

چون در مقایسه دو مدل، مجموعه هدف باید یکسان باشد. اگر یک مدل روی ردیف‌های آسان‌تر یا دارای تاریخچه
بیشتر امتیاز بگیرد، اختلاف metric ممکن است ناشی از تفاوت نمونه باشد نه کیفیت مدل.

### چرا فقط تعداد paired کافی نیست؟

چون ۴۰ هزار ردیف بدون دانستن مخرج معنای کاملی ندارد. coverage نشان می‌دهد چه سهمی از داده قابل
مقایسه بوده و علت‌های حذف نشان می‌دهند آیا مدل فصلی نسبت به سری‌های کوتاه سوگیری پوشش دارد یا نه.

### آیا پوشش پایین یعنی مدل بد است؟

نه الزاماً. ممکن است مدل فصلی به‌طور طبیعی ۵۲ هفته تاریخ بخواهد. اما پوشش پایین دامنه اعتبار نتیجه
را محدود می‌کند و باید کنار metric گزارش شود.
