# بازبینی همه‌جانبه و آزمون‌های غافلگیرانه PromoGuard — نسخه 0.6.4

تاریخ بازبینی: ۱۴۰۵/۰۶/۱۵ (2026-09-06)

این سند توضیح ساده، کامل و قابل ارائهٔ بازبینی اصلی پروژه است. هدف این مرحله اضافه‌کردن یک مدل
پرزرق‌وبرق نبود؛ هدف این بود که ببینیم وقتی داده بد، ورودی غیرمنتظره، نمونه خیلی کوچک، خطای نسخه،
یا یک سؤال سخت آماری وارد سیستم می‌شود، برنامه درست متوقف می‌شود یا بی‌صدا جواب غلط می‌دهد.

## نتیجه در یک جمله

نسخه 0.6.4 برای **دموی محلی، رزومه و benchmark مهندسی روی داده عمومی واقعی قابل اتکا است**، اما
هنوز برای تصمیم خودکار قیمت/بودجه، ادعای سود واقعی، تعمیم به بازار ایران یا مقاله علمی نهایی مجاز
نیست. به زبان ساده: موتور آزمایشگاهی درست کار می‌کند، ولی هنوز گواهینامه رانندگی در خیابان واقعی را
ندارد.

## اول: پروژه اصلاً چه کار می‌کند؟

PromoGuard دو مسیر داده را عمداً جدا نگه می‌دارد:

1. داده واقعی فروشگاهی dunnhumby برای کنترل کیفیت، پیش‌بینی فروش عادی و ممیزی مشاهده‌ای پروموشن؛
2. داده واقعی آزمایش تصادفی Criteo برای تمرین و ارزیابی روش‌های uplift و Qini.

مسیر اول می‌گوید «فروش دیده‌شده با یک خط مبنای ساده چقدر فرق دارد؟» اما نمی‌گوید پروموشن علت این
فرق بوده است. مسیر دوم چون treatment در آزمایش Criteo تصادفی است، اجازه می‌دهد کیفیت رتبه‌بندی
uplift را در همان benchmark بررسی کنیم؛ ولی نتیجه Criteo به فروشگاه ایرانی یا پروموشن SKU منتقل
نمی‌شود.

## معماری به زبان ساده

```text
فایل واقعی
   ↓
قرارداد و کنترل کیفیت داده
   ↓
پنل استاندارد هفته × فروشگاه × کالا
   ├── پیش‌بینی زمان‌محور بدون دیدن آینده
   ├── ممیزی مشاهده‌ای + هشدار + امکان abstain
   ├── API محلی با قرارداد typed
   └── داشبورد فارسی برای داور

فایل واقعی آزمایش Criteo
   ↓
split پایدار و مستقل از outcome
   ↓
S-Learner / T-Learner / nonlinear S-Learner
   ↓
انتخاب فقط با validation
   ↓
Qini + bootstrap + balance/overlap + مرز ادعا
```

## چه تست‌های غافلگیرانه‌ای اجرا شد؟

### ۱. داده بی‌نهایت (`inf`)

عدد بی‌نهایت از نظر Python ممکن است «عدد» به نظر برسد. نسخه قبلی می‌توانست `inf` مثبت را منفی یا
خالی تشخیص ندهد. این مقدار بعداً میانگین، نمودار یا JSON را خراب می‌کرد. اکنون `inf` و `-inf` در
داده فروش و در score مدل قبل از تحلیل رد می‌شوند.

### ۲. شناسه‌هایی که ظاهراً فرق دارند ولی در واقع یکی‌اند

`"1"` و `" 1 "` بعد از حذف فاصله یک فروشگاه هستند. تاریخ‌های `2024-01-07` و
`2024-01-07T00:00:00` نیز یک هفته را نشان می‌دهند. duplicate باید بعد از نرمال‌سازی شناسه و تاریخ
بررسی شود؛ این ترتیب اکنون تست و قفل شده است.

### ۳. فایل محلی بسیار بزرگ

upload از قبل سقف ۱۲۰ MiB داشت، ولی endpoint مسیر محلی می‌توانست قبل از بررسی تعداد ردیف کل فایل را
در حافظه بخواند. اکنون مسیر محلی نیز قبل از `read_csv` با سقف بایت کنترل می‌شود. پنل واقعی پروژه
حدود 104.7 MB است و از این gate عبور می‌کند.

### ۴. هیچ رویداد پروموشن واجد شرایط نیست

در نسخه قبلی، انتخاب خودکار رویداد بیرون از بلوک مدیریت خطا بود و می‌توانست به خطای داخلی 500
تبدیل شود. اکنون API پاسخ کنترل‌شده 422 و پیام قابل فهم می‌دهد.

### ۵. داده فقط treated یا فقط control دارد

Qini بدون هر دو گروه تعریف معتبری ندارد. نسخه قبلی در این حالت warning تقسیم بر صفر و `NaN` تولید
می‌کرد. اکنون محاسبه صریحاً با `ValueError` متوقف می‌شود. این رفتار بهتر است، چون شکست واضح از عدد
ظاهراً معتبر اما بی‌معنا امن‌تر است.

### ۶. score کوتاه‌تر، بلندتر یا غیرمتناهی است

طول score باید دقیقاً با تعداد ردیف برابر باشد و همه scoreها باید finite باشند. هر دو قرارداد اکنون
قبل از sort و محاسبه Qini بررسی می‌شوند.

### ۷. bootstrap روی نمونه خیلی کوچک

در Poisson multiplier bootstrap ممکن است یک draw کوچک پس از وزن‌دهی هیچ treated یا control نداشته
باشد. نسخه قبلی می‌توانست آن draw نامعتبر را وارد فاصله اطمینان کند یا بر صفر تقسیم شود. اکنون draw
نامعتبر حذف، draw جایگزین تولید و تعداد drawهای حذف‌شده در artifact ثبت می‌شود.

### ۸. وابستگی نمونه train به treatment یا outcome

ماسک نمونه train با treatment، visit و conversion دستکاری‌شده دوباره محاسبه شد. ماسک باید دقیقاً
یکسان بماند. تست جدید ثابت می‌کند نمونه‌گیری فقط ویژگی‌های پیش‌درمان `f0` تا `f11` را می‌بیند.

### ۹. پیش‌بینی با پارامتر lag صفر یا منفی

seasonal period صفر/منفی از نظر زمانی بی‌معنا و بالقوه باعث نگاه اشتباه به آینده است. اکنون قبل از
پیش‌بینی رد می‌شود. تست قدیمی invariance آینده نیز همچنان پاس است: تغییر داده بعد از پنجره test
نمی‌تواند پیش‌بینی گذشته را تغییر دهد.

### ۱۰. اجرای واقعی داشبورد

فقط helperهای UI تست نشدند. Streamlit به‌صورت headless اجرا شد، سپس پنل واقعی ۵۲۴٬۹۵۰ ردیفی
بارگذاری و ممیزی رویداد نماینده اجرا شد. نتیجه:

- ۳٬۹۰۹ سری فروشگاه–کالا؛
- ۱۴۹٬۳۸۶ ردیف پروموشن؛
- رویداد `23345-2840004768-2010-01-13`؛
- فروش مشاهده‌شده ۱۲۸ واحد؛
- خط مبنا ۱۸۵ واحد؛
- اختلاف مشاهده‌ای منفی ۵۷ واحد؛
- recommendation برابر `needs_more_evidence`؛
- بدون exception یا error رابط.

یک AppTest سبک نیز به CI اضافه شد تا import و render اولیه داشبورد روی ماشین تمیز بررسی شود.

### ۱۱. نسخه واقعی پکیج و API

یک ایراد release مهم پیدا شد: tag و `pyproject.toml` نسخه 0.6.3 داشتند، ولی پکیج و endpoint health
هنوز 0.5.2 گزارش می‌کردند. تست قدیمی نیز اشتباه قدیمی را تأیید می‌کرد. اکنون فقط یک منبع نسخه در
`promoguard.__version__` وجود دارد و setuptools نسخه wheel را از همان می‌خواند. تست health بررسی
می‌کند نسخه API، پکیج نصب‌شده و metadata یکسان باشند.

### ۱۲. امنیت کد و dependency

دو اسکن مستقل اجرا شد:

- Bandit ابتدا یک `assert` در مسیر اجرایی T-Learner پیدا کرد. `assert` با اجرای optimized ممکن است
  حذف شود؛ آن را با خطای صریح runtime جایگزین کردیم. اجرای نهایی Bandit هیچ finding ندارد.
- pip-audit ابتدا آسیب‌پذیری شناخته‌شده در pytest قدیمی و setuptools قدیمی محیط پیدا کرد. حداقل
  نسخه امن در قرارداد توسعه/build ثبت و محیط ارتقا داده شد. اجرای نهایی آسیب‌پذیری شناخته‌شده‌ای در
  dependencyهای نصب‌شده پیدا نکرد. خود `promoguard-ai` چون پکیج محلی و منتشرنشده در PyPI است از
  جست‌وجوی PyPI صرف‌نظر می‌شود؛ این finding نیست.

## اصلاح مهم آماری: سه «نرخ» یک چیز نیستند

در artifact قبلی این مقدار وجود داشت:

```text
incremental_rate = cumulative Qini / all prefix rows
```

نام آن می‌توانست این تصور را ایجاد کند که مقدار بالا ATE یا اثر متوسط هر فرد است. این درست نیست،
چون convention فعلی Qini با تعداد treated مقیاس می‌شود. اکنون سه مقدار جدا داریم:

### Qini به‌ازای جمعیت رتبه‌بندی‌شده

```text
qini_per_ranked_row = cumulative Qini / prefix population
```

این مقدار برای خواندن مقیاس منحنی مفید است، ولی ATE نیست.

### اختلاف مستقیم نرخ دو گروه

```text
difference_in_means_incremental_rate
  = treated visit rate - control visit rate
  = cumulative Qini / treated rows
```

این مقدار در یک زیرگروه دارای هر دو arm، اختلاف نرخ پاسخ مشاهده‌شده تحت randomization است.

### برآورد IPW

```text
ipw_incremental_rate
  = mean(T×Y/p - (1-T)×Y/(1-p))
```

این برآورد از احتمال treatment کل آزمایش استفاده می‌کند و یک cross-check design-based است. لازم
نیست دقیقاً با اختلاف مستقیم دو نرخ برابر شود.

در ۲۰٪ اول رتبه‌بندی مدل منتخب روی test واقعی:

| مقدار | نتیجه | معنی درست |
|---|---:|---|
| ردیف‌های prefix | 419,459 | ۲۰٪ بالای رتبه‌بندی |
| treated / control | 359,478 / 59,981 | پوشش هر دو arm |
| Qini تجمعی | 14,135.19 | مقدار تجمعی با convention ثبت‌شده |
| Qini / جمعیت prefix | 0.03370 | شاخص مقیاس منحنی؛ ATE نیست |
| اختلاف نرخ treated-control | 0.03932 | اختلاف مستقیم پاسخ در prefix |
| IPW | 0.04720 | cross-check وزن‌دهی‌شده |

هیچ‌کدام «۳.۳٪ سود»، «۴.۷٪ ROI» یا «اثر بازار ایران» نیستند.

## فازهای باقی‌مانده از این نقطه

### Phase 8 — قرارداد ورودی واقعی و optimizer محدودشده

اول باید schema واقعی margin، trade spend، بودجه، موجودی، محدودیت قیمت و ظرفیت فروشگاه تعریف شود.
اگر این داده‌ها وجود نداشته باشند سیستم باید `insufficient_business_inputs` بدهد، نه عدد فرضی. بعد
می‌توان optimizer سناریو ساخت که فقط پیشنهاد برای تأیید انسان می‌دهد.

### Phase 9 — زیرساخت تولید و AI کنترل‌شده

run metadata، DuckDB/PostgreSQL، pipeline idempotent، logging، data/model drift و مانیتورینگ اضافه
می‌شوند. بعد یک لایه LLM می‌تواند فقط JSON typed را توضیح دهد. LLM اجازه تغییر عدد، حذف هشدار یا
ساخت ادعای سود ندارد و برنامه بدون API key هم باید کار کند.

### Phase 10 — بسته نهایی رزومه و استخدام

README دو زبانه، ویدیوی کوتاه، case study، نمودار معماری، جدول mapping با آگهی‌های Data Scientist و
Applied AI، و دستور بازتولید زیر ده دقیقه آماده می‌شود. داور باید در ۶۰ ثانیه ارزش و صداقت پروژه را
بفهمد.

### Track پژوهشی اختیاری — برای شانس مقاله

برای مقاله قوی‌تر، یک dataset یا holdout تازه، repeated cross-fitting، model-refit bootstrap،
چند seed/split از پیش ثبت‌شده، مقایسه DR/X/R-Learner و تحلیل calibration/policy risk لازم است. این
track با نسخه رزومه یکی نیست و نباید به‌خاطر عجله محصول را متوقف کند.

7. شروع track مقاله فقط پس از freeze پروتکل و تهیه داده/holdout تازه.

## نتیجهٔ نهایی CI و درسی که باید بلد باشی

در اولین اجرای CI سخت‌گیرانه، تست‌ها، پوشش، Ruff، compileall، `pip check` و Bandit همگی موفق شدند،
اما `pip-audit` نسخهٔ `setuptools 79.0.1` خود Runner گیت‌هاب را آسیب‌پذیر اعلام کرد. این خطا از کد
PromoGuard نبود، ولی یک مشکل واقعی در محیط ساخت بود و نباید نادیده گرفته می‌شد.

علت ساده این است: بخش `build-system` پروژه ابزار ساخت را داخل یک محیط موقت و ایزوله به‌روزرسانی
می‌کند؛ در نتیجه نسخهٔ قدیمی نصب‌شده روی Runner همچنان باقی می‌ماند و ممیزی امنیتی همان را می‌بیند.
workflow اصلاح شد تا پیش از نصب پروژه، `pip` و `setuptools` محیط اصلی Runner نیز صریحاً به نسخهٔ امن
ارتقا پیدا کنند. اجرای بعدی با شناسهٔ
[34223222775](https://github.com/RezaAshrafii/promoguard-retail-intelligence/actions/runs/34223222775)
روی Ubuntu و Python 3.11 تمام gateها، از جمله `pip-audit` و ساخت wheel، را با موفقیت گذراند.

پس اگر داور پرسید «چرا تست محلی کافی نبود؟» پاسخ این است: چون محیط Linux گیت‌هاب با ویندوز توسعه
فرق دارد و dependencyهای خود Runner هم باید بررسی شوند. CI مستقل ثابت می‌کند نتیجه فقط روی لپ‌تاپ
سازنده کار نمی‌کند.
