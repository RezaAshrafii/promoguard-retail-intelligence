# آموزش Phase 8.1 — قرارداد داده واقعی اقتصاد پروموشن

## این مرحله خیلی ساده چه کار می‌کند؟

فرض کن می‌خواهیم بگوییم کدام تخفیف از نظر مالی قابل اجراست. قبل از هر مدل باید بدانیم قیمت عادی،
قیمت تخفیف، هزینه کالا، کمک تأمین‌کننده، هزینه کمپین، موجودی و بودجه واقعاً چقدر هستند. دیتاست عمومی
فعلی همه این ستون‌ها را ندارد. بنابراین عددی اختراع نکردیم؛ یک «فرم ورودی ماشینی سخت‌گیرانه» ساختیم
که شریک واقعی آینده باید آن را با منبع پر کند.

## معماری

```text
partner export / approved contract / model output / approved assumption
                              ↓
                   OptimizationInput contract
                              ↓
             deterministic feasibility checks
                              ↓
        eligible یا infeasible + همه علت‌ها + limitation
```

در این مرحله هیچ سناریویی انتخاب یا اجرا نمی‌شود و عبارت «سود پیش‌بینی‌شده» تولید نمی‌کنیم.

## فایل‌ها

- `src/promoguard/optimization/contracts.py`: شکل دقیق ورودی، evidence و قوانین ساختاری؛
- `src/promoguard/optimization/feasibility.py`: کنترل شش محدودیت بدون انتخاب سناریو؛
- `src/promoguard/optimization/__init__.py`: رابط عمومی ماژول؛
- `tests/unit/test_optimization_contracts.py`: تست‌های مثبت، منفی و غافلگیرانه؛
- `docs/decisions/0009-real-economics-input-before-optimization.md`: دلیل تصمیم معماری؛
- `docs/phase-08-real-input-contract.md`: قرارداد فنی و درخواست داده شریک؛
- `reports/phase-08/phase-08-1-quality-report.json`: شاهد ماشین‌خوان اجرای gate.

## چرا برای پول از Decimal استفاده شد؟

عدد اعشاری معمولی کامپیوتر (`float`) بعضی مبالغ را دقیق نگه نمی‌دارد. `Decimal` محاسبه قیمت، هزینه
و بودجه را قابل پیش‌بینی‌تر می‌کند. تقاضا همچنان می‌تواند اعشاری باشد، چون خروجی مدل است و لزوماً
تعداد شمارش‌شده نهایی نیست.

## evidence یعنی چه؟

برای هر عدد مهم می‌پرسیم: «از کجا آمده، مربوط به چه تاریخی است و چه کسی آن را تأیید کرده؟» اگر فقط
یک فرض مدیریتی باشد، برچسب `approved_assumption` می‌گیرد؛ فرض را به داده مشاهده‌شده تبدیل نمی‌کنیم.

## شش علت رد سناریو

1. قیمت پروموشن از قیمت عادی بیشتر باشد؛
2. درصد تخفیف از سقف مجاز بیشتر باشد؛
3. موجودی حتی reserve را پوشش ندهد؛
4. کران بالای تقاضای پیش‌بینی‌شده از موجودی قابل فروش بیشتر باشد؛
5. contribution هر واحد از کف مورد قبول کمتر باشد؛
6. trade spend پیش‌بینی‌شده از بودجه بیشتر باشد.

سیستم همه علت‌ها را با هم برمی‌گرداند تا مدیر فقط اولین خطا را نبیند.

## چه چیزی هنوز ساخته نشده؟

Optimizer، رتبه‌بندی سناریو، انتخاب چند SKU تحت بودجه مشترک، تحلیل حساسیت کامل و API/UI این بخش هنوز
ساخته نشده‌اند. این‌ها Phase 8.2 هستند و باید روی ورودی واقعی یا فرض‌های کاملاً برچسب‌خورده اجرا شوند.

## سؤال‌های احتمالی جلسه

**چرا مستقیماً optimizer نساختید؟** چون بدون cost، inventory و trade spend واقعی، خروجی مالی فقط
ظاهر دقیق دارد و قابل دفاع نیست.

**آیا approved assumption داده واقعی است؟** خیر. فقط فرض تأییدشده برای what-if است و برچسبش حفظ
می‌شود.

**eligible یعنی سودآور است؟** خیر. فقط یعنی شش محدودیت تعریف‌شده را نقض نکرده است.

**چرا human approval همیشه true است؟** چون محصول فعلی تصمیم‌یار است و اجازه تغییر خودکار کمپین
ندارد.

**چرا upper تقاضا با inventory مقایسه می‌شود؟** برای یک کنترل محافظه‌کارانه؛ نقطه پیش‌بینی ممکن است
کم باشد ولی کران بالای آن ریسک stockout را نشان دهد.
