# راهنمای ساده: جلوگیری از محاسبهٔ تکراری گزارش

اگر یک فایل و یک کمپین را دوباره بررسی کنیم، بهتر است نتیجهٔ یکسان را از نو محاسبه نکنیم. این
مرحله برای همین کار است؛ اما cache نباید باعث شود گزارش یک فایل یا کمپین دیگر اشتباهی برگردد.

## کلید cache از چه چیزهایی ساخته می‌شود؟

سامانه یک fingerprint از این موارد می‌سازد:

- checksum کامل محتوای فایل؛ نام فایل کافی نیست، چون ممکن است دو نسخه اسم یکسان داشته باشند.
- فروشگاه، کالا و تاریخ شروع کمپین انتخاب‌شده.
- نسخهٔ محصول و نسخهٔ سیاست ممیزی.
- نسخهٔ قرارداد خروجی گزارش.

اگر هرکدام عوض شود، کلید فرق می‌کند و محاسبهٔ تازه انجام می‌شود. بنابراین یک فایل ثابت برای دو
کمپین مختلف یک نتیجه مشترک نمی‌گیرد.

## وقتی کاربر گزارش می‌خواهد چه می‌شود؟

1. `report_id` تازه برای هر درخواست ساخته می‌شود؛ پس دو درخواست گزارش جداگانه قابل پیگیری‌اند.
2. پس‌زمینه cache را با fingerprint دقیق جست‌وجو می‌کند.
3. اگر نتیجهٔ معتبر وجود داشته باشد، همان دادهٔ گزارش خوانده می‌شود و `cache_hit=true` ثبت
   می‌شود.
4. اگر وجود نداشته باشد، ممیزی اجرا می‌شود، نتیجه به شکل فایل موقت کامل نوشته و با جابه‌جایی
   اتمی ذخیره می‌شود. سپس `cache_hit=false` است.
5. PDF جداگانه برای `report_id` ساخته می‌شود، حتی اگر عددهای گزارش از cache آمده باشند.

فایل cache فقط خروجی محاسبه را نگه می‌دارد؛ اسم مسیر محلی فایل منبع به خروجی گزارش اضافه
نمی‌شود.

## تست‌های حفاظتی

- درخواست یکسان باید بار اول `cache_hit=false` و بار دوم `true` بدهد و payload یکسان بماند.
- تغییر checksum فایل، کلید را عوض می‌کند.
- تغییر تاریخ شروع رویداد هم کلید را عوض می‌کند.
- شناسهٔ گزارش هر بار جدید می‌ماند؛ cache به معنی یکی‌شدن گزارش‌ها نیست.

## محدودیت مهم

این cache روی دیسک محلی است و registry شناسه‌ها در حافظهٔ API است. اگر API خاموش/روشن شود،
درخواست تازه می‌تواند cache را دوباره استفاده کند، اما `GET` شناسهٔ گزارش قدیمی هنوز از دیتابیس
پایدار بازیابی نمی‌شود. برای سرویس چندکاربره باید storage تراکنشی، قفل/هم‌آهنگی چند worker،
سیاست انقضا و حذف، دسترسی سازمانی و اعتبارسنجی schema ذخیره‌سازی طراحی شود. cache فعلی اثبات
production readiness نیست.
