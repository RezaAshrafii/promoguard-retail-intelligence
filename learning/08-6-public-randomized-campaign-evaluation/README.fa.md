# راهنمای سادهٔ ارزیابی کمپین با دادهٔ واقعی Hillstrom

## این مرحله چه مسئله‌ای را حل می‌کند؟

تا پیش از این، محصول عمدتاً می‌توانست آماده‌بودن داده یا تفاوت فروش مشاهده‌شده با یک خط مبنا را نشان دهد. این نوع بررسی برای فروش هفتگی فروشگاه مفید است، اما چون کمپین در آن داده‌ها تصادفی تعیین نشده، به‌تنهایی ثابت نمی‌کند خود کمپین باعث تغییر فروش شده است.

برای اینکه بتوانیم رفتار یک موتور قضاوت آماری را روی دادهٔ واقعی و بدون دادهٔ ساختگی امتحان کنیم، یک مسیر جداگانه برای یک آزمایش بازاریابی عمومی اضافه شد. در دادهٔ Hillstrom، طبق توضیح ناشر، افراد به سه گروه تخصیص یافته‌اند: ایمیل محصولات مردانه، ایمیل محصولات زنانه، یا بدون ایمیل. بعد از ارسال ایمیل، خرید، بازدید و مبلغ خرید طی دو هفته ثبت شده است. ناشر و لینک داده در [صفحهٔ اصلی داده](https://blog.minethatdata.com/2008/03/minethatdata-e-mail-analytics-and-data.html) آمده‌اند.

این داده تخفیف فروشگاهی نیست؛ در نتیجه این مسیر روش مقایسهٔ کمپین را نشان می‌دهد، نه اینکه PromoGuard اکنون برای هر تخفیف فروشگاهی حکم سود قطعی می‌دهد.

## کاربر چه چیزی می‌بیند؟

در صفحهٔ `/experiments` معیار اصلی را انتخاب می‌کند:

- مبلغ خرید در دو هفته؛
- احتمال خرید؛
- احتمال بازدید.

اگر هدفی از سمت کسب‌وکار تعریف شده باشد، می‌تواند حداقل اثر موردنیاز را وارد کند. اگر هدف را وارد نکند، برنامه فقط می‌گوید داده با افزایش، کاهش یا نتیجهٔ نامشخص سازگار است. «از صفر بالاتر» به معنی «سودآور» یا «به‌اندازهٔ کافی خوب» نیست.

بعد از زدن دکمه، API یک شناسهٔ گزارش می‌سازد و کار را در پس‌زمینه انجام می‌دهد. صفحه وضعیت را می‌پرسد و در پایان تعداد افراد، میانگین‌ها، اختلاف هر نفر، اثر برآوردی به‌ازای هزار نفر، بازهٔ عدم‌قطعیت و مقایسهٔ مستقیم دو نوع ایمیل را نشان می‌دهد. گزارش با شناسه قابل بازیابی است و بر اساس نسخهٔ داده و تنظیمات cache می‌شود.

## عدد واقعی این اجرا چه می‌گوید؟

در نتیجهٔ پیش‌فرض، پیامد اصلی مبلغ ناخالص خرید به‌ازای هر فرد تخصیص‌یافته است:

| مقایسه | اختلاف میانگین هر فرد | بازهٔ هم‌زمان ۹۵٪ | تفسیر محدود |
|---|---:|---:|---|
| ایمیل مردانه در برابر بدون ایمیل | حدود ۰٫۷۷ دلار بیشتر | ۰٫۴۲ تا ۱٫۱۲ دلار | بازه بالای صفر است |
| ایمیل زنانه در برابر بدون ایمیل | حدود ۰٫۴۲ دلار بیشتر | ۰٫۱۱ تا ۰٫۷۴ دلار | بازه بالای صفر است |
| ایمیل مردانه در برابر زنانه | حدود ۰٫۳۵ دلار بیشتر | منفی ۰٫۰۴ تا مثبت ۰٫۷۳ دلار | برتری روشن نیست |

این مبالغ را نباید «سود» نامید. فایل، هزینهٔ ایمیل، تخفیف، بهای تمام‌شده و حاشیهٔ سود ندارد. همچنین این آزمایش دربارهٔ بازار ایمیل قدیمی ناشر است و نتیجه‌اش را نمی‌شود به شرکت ایرانی یا پروموشن کالای فروشگاهی تعمیم داد.

## از کجا آمد این بازهٔ اطمینان؟

هر مقایسه اختلاف میانگین پیامد در دو گروه مستقل را حساب می‌کند. چون اندازهٔ دو گروه ممکن است متفاوت باشد و پراکندگی‌شان هم برابر فرض نمی‌شود، از خطای استاندارد Welch با واریانس جداگانه استفاده می‌کنیم. به‌دلیل بزرگ بودن گروه‌ها، بازه با تقریب نرمال محاسبه می‌شود.

سه مقایسه از قبل تعیین شده‌اند. اگر برای هر کدام جداگانه بازهٔ ۹۵درصدی بسازیم، احتمال اینکه دست‌کم یکی از سه بازه تصادفاً گمراه‌کننده باشد بالا می‌رود. Bonferroni مقدار بحرانی را سخت‌گیرانه‌تر می‌کند تا پوشش کلی سه مقایسه نزدیک ۹۵٪ بماند. این روش محافظه‌کارانه است و ممکن است نتیجه را نامشخص‌تر کند؛ این هزینهٔ مقایسهٔ هم‌زمان است.

حداقل ۱٬۰۰۰ ردیف در هر دو بازوی یک مقایسه لازم است تا برنامه برچسب جهت آماری بدهد. پایین‌تر از آن، اختلاف و بازه قابل دیدن است، اما وضعیت «نمونه ناکافی» خواهد بود. این حد یک قاعدهٔ محافظه‌کارانهٔ اجرایی است، نه جایگزین محاسبهٔ توان آماری برای یک پایلوت واقعی.

## چرا ردیف‌های تکراری را حذف نکردیم؟

داده شناسهٔ یکتای مشتری ندارد و ۶٬۵۶۲ ردیف کاملاً یکسان وجود دارد. دو مشتری متفاوت ممکن است سابقه، گروه و خرید یکسانی داشته باشند. اگر ردیف‌های مشابه را حذف می‌کردیم، ممکن بود افراد واقعی را دور بریزیم. پس تکرارها گزارش می‌شوند و حفظ می‌شوند؛ «ردیف مشابه» را اشتباهاً «مشتری تکراری» نمی‌نامیم.

## معماری، به زبان ساده

```text
CSV عمومی محلی
  -> بررسی قرارداد و کیفیت
  -> محاسبهٔ اثرهای ازپیش‌تعریف‌شده در بستهٔ Python
  -> ذخیرهٔ گزارش تجمیعی با report ID و cache
  -> API وضعیت را برمی‌گرداند
  -> صفحهٔ Next.js عددها و محدودیت‌ها را نمایش می‌دهد
```

فرمول‌ها در `src/promoguard/experiments/hillstrom.py` هستند، نه در صفحهٔ وب. API فقط درخواست را اعتبارسنجی و کار را زمان‌بندی می‌کند. مرورگر هیچ عددی را خودش محاسبه نمی‌کند. این جداسازی کمک می‌کند نتیجه در CLI، API و وب از یک محاسبهٔ واحد بیاید.

## فایل‌های این مرحله

- `src/promoguard/experiments/hillstrom.py`: قرارداد، اعتبارسنجی، اثر، بازه و وضعیت احتیاطی.
- `src/promoguard/cli.py`: فرمان اجرای ارزیابی و ساخت گزارش JSON.
- `tools/download_hillstrom.py`: دانلود از ناشر؛ بدون بازنویسی تصادفی فایل قبلی.
- `apps/api/contracts.py` و `apps/api/main.py`: درخواست، شناسهٔ گزارش، اجرای پس‌زمینه و cache.
- `frontend/app/experiments/page.tsx`: صفحهٔ انتخاب پیامد، اجرای تحلیل و نمایش نتیجه.
- `frontend/app/page.tsx` و `frontend/app/globals.css`: لینک صفحه و سبک بصری.
- `tests/unit/test_hillstrom_experiment.py`: دادهٔ نامعتبر، تکرارها، اثرها، بازه و abstention.
- `tests/integration/test_api.py` و `tests/integration/test_cli.py`: API، ذخیره/cache و CLI.
- `docs/data/hillstrom-experiment-benchmark-fa.md`: منبع، روش، مجوز و محدودیت‌ها.
- `reports/hillstrom/hillstrom-experiment-report.json`: خروجی تجمیعی بازتولیدشده.
- `ROADMAP.md` و `README.md`: وضعیت محصول و دروازهٔ پروژه.

فایل خام در `data/raw/hillstrom/` نگهداری می‌شود و Git آن را نادیده می‌گیرد. ناشر در صفحهٔ عمومی مجوز روشن بازتوزیع ثبت نکرده؛ برای همین فایل CSV را داخل GitHub قرار نمی‌دهیم. SHA-256 ثبت‌شده کمک می‌کند بفهمیم فایل محلی همان نسخهٔ ارزیابی‌شده است.

## اجرا و آزمون

```powershell
python tools/download_hillstrom.py
python -m promoguard.cli experiment-evaluate `
  --input data/raw/hillstrom/hillstrom-email-analytics-2008.csv `
  --output reports/hillstrom
python -m pytest tests/unit/test_hillstrom_experiment.py -q
python -m ruff check src/promoguard/experiments/hillstrom.py src/promoguard/cli.py apps/api/main.py apps/api/contracts.py tests/unit/test_hillstrom_experiment.py tests/integration/test_api.py tests/integration/test_cli.py
python -m compileall -q src apps
```

برای اجرای وب، ابتدا API را با دستور معمول پروژه بالا بیاور و سپس در پوشهٔ `frontend` اجرا کن:

```powershell
npm run dev
```

صفحه در `/experiments` است. اگر دیتاست در محل محلی نیست، API به‌جای گزارش ساختگی خطای روشن می‌دهد و راه دانلود را نشان می‌دهد.

## چه چیزی هنوز تصمیم انسانی می‌خواهد؟

کد می‌تواند اثر برآوردی و عدم‌قطعیت را حساب کند، ولی نمی‌تواند خودش تصمیم بگیرد چه مقدار افزایش برای یک کسب‌وکار ارزشمند است. مدیر باید حداقل اثر قابل‌قبول را تعیین کند و هزینهٔ کمپین، هزینهٔ تخفیف و حاشیهٔ سود را بدهد. برای تخفیف فروشگاهی باید دادهٔ رویداد تخفیف، کالا/فروشگاه، زمان، موجودی و قیمت/هزینه داشته باشیم و ابتدا روش را روی طراحی آزمایشی یا پایلوت مناسب اعتبارسنجی کنیم.

هیچ تصمیم انسانی برای ادامهٔ پیاده‌سازی همین benchmark لازم نیست؛ فقط برای تبدیل آن به قضاوت تجاری واقعی باید آستانه و اقتصاد واقعی تعریف شود. این فاز نیز به‌تنهایی Phase 8 را کامل نمی‌کند و جای دادهٔ مجاز شرکت و بازبینی مدیر فروش را نمی‌گیرد.

## پرسش‌هایی که ممکن است ازت بپرسند

**این داده واقعاً واقعی است؟** بله، فایل عمومی منتشرشده توسط منبع پروژهٔ MineThatData است؛ نه دادهٔ ساختگی ما. نگهداری محلی و hash آن ثبت شده، اما مجوز بازتوزیع صریح پیدا نشده است.

**می‌توانی بگویی ایمیل باعث درآمد شد؟** من فقط بر اساس طراحی تصادفی توصیف‌شده از سوی ناشر اثر intention-to-treat بر پیامدهای ثبت‌شده را برآورد می‌کنم. ادعای من محدود به همین benchmark و همین بازه است؛ سود یا تعمیم به بازار دیگر را نمی‌گویم.

**پس چرا مستقیم نمی‌گویی کمپین خوب بوده؟** چون «خوب» به هدف و اقتصاد شرکت بستگی دارد. افزایش درآمد ناخالص بدون دانستن هزینه و حاشیهٔ سود می‌تواند حتی زیان‌ده باشد.

**چرا سه مقایسه داری؟** دو ایمیل باید هر کدام با کنترل مقایسه شوند و مدیر همچنین ممکن است بخواهد بداند کدام نسخه برتر است. سه مقایسه از قبل تعریف شده‌اند و اصلاح Bonferroni جلوی انتخاب گزینشی بازهٔ خوشایند را می‌گیرد.

**بزرگ‌ترین محدودیت چیست؟** این دادهٔ ایمیل است، نه تخفیف کالا؛ قدیمی و غیرایرانی است؛ هزینه و سود ندارد؛ و مجوز بازتوزیع واضحی روی صفحهٔ ناشر درج نشده است.

## وضعیت اعتبارسنجی

در بازبینی نهایی این مرحله:

- کل suite پایتون: **۲۲۶ تست پاس شد**.
- Ruff برای تمام فایل‌های Python مربوط به این مسیر: پاس شد.
- `compileall` برای `src`، `apps` و `tools`: پاس شد.
- `python -m promoguard.cli health`: پیام سلامت هسته را برگرداند.
- `npm run typecheck` و `npm run build`: پاس شدند؛ صفحهٔ `/experiments` به‌صورت static تولید شد.
- آزمون زنده: صفحهٔ Next و OpenAPI هر دو HTTP 200 دادند؛ درخواست ساخت گزارش ۲۰۲ گرفت و گزارش با سه مقایسه به وضعیت `ready` رسید.
- عدد اثر ایمیل مردانه در آزمون زنده، `0.7698` دلار برای هر فرد بود و با خروجی JSON بازتولیدشده برابر بود.
- یک تست قدیمی Streamlit ابتدا به‌خاطر timeout بیست‌ثانیه‌ای شکست خورد. اجرای تشخیصی نشان داد صفحه بدون exception در ۲۳٫۶ ثانیه کامل می‌شود؛ مهلت دو تست dashboard به ۶۰ ثانیه رسید و بعد کل suite با ۲۲۶ پاس تمام شد.
- Ruff سراسری هنوز ۸ ایراد قدیمی import/unused-import در چند ابزار PDF و آماده‌سازی benchmark گزارش می‌کند. آن فایل‌ها خارج از این کار بودند و تغییر داده نشدند؛ lint فایل‌های همین مرحله تمیز است.
- یک هشدار deprecation از ترکیب `starlette.testclient` و `httpx` باقی است؛ آزمون‌ها پاس‌اند، ولی این وابستگی در یک کار نگهداری جداگانه باید به‌روزرسانی شود.

این اجرا با مدل فعلی Codex محیط انجام شد؛ انتخاب یا تعویض مدل در ابزار اجرای این کار در دسترس نبود و بازبینی مستقل دیگری انجام نشده است. عبور تست‌ها مدرک صحت نرم‌افزاری این پیاده‌سازی است، نه تأیید مستقل روش‌شناسی یا اثبات سود تجاری. فاز 8 کلان همچنان باز است.
