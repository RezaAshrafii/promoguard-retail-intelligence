# راهنمای مرحلهٔ سیاست تصمیم مدیریتی

## این مرحله چه چیزی را اضافه کرد؟

تا پیش از این برنامه می‌توانست سود افزایشی مشروط یک سناریو را در سه حالت تقاضا نشان دهد. اما نمی‌دانست چه مقدار نتیجه برای یک شرکت «ارزشمند» است. این مقدار به هدف شرکت بستگی دارد؛ مثلاً ممکن است مدیر حداقل ۵۰۰ هزار ریال سود افزایشی بخواهد، یا هزینهٔ فرصت دیگری داشته باشد.

در این مرحله درخواست باید آستانه را همراه ارز، مرجع، نام تأییدکننده و تاریخ داشته باشد. برنامه آستانه را از خودش حدس نمی‌زند؛ ولی نام و مرجع فقط دادهٔ ثبت‌شده‌اند و هویت مدیر یا واقعیت تأیید را احراز نمی‌کنند.

## چهار حالت خروجی

1. `blocked_by_constraints`: سناریو یکی از محدودیت‌های موجودی، بودجه، تخفیف یا حاشیهٔ واحد را رد کرده است.
2. `candidate_for_human_review`: حتی حد پایین سناریوی تقاضا از آستانهٔ مدیر بالاتر است. این یعنی «ارزش بررسی انسانی دارد»، نه مجوز اجرا.
3. `below_manager_hurdle`: حتی حد بالای سناریوی تقاضا به آستانه نمی‌رسد. این به‌تنهایی دستور توقف کمپین نیست.
4. `hurdle_not_resolved`: بازه از آستانه عبور می‌کند؛ با این داده نمی‌شود تفاوت را روشن کرد و باید داده یا آزمایش بهتری داشت.

حد پایین و بالا در این نسخه «حالت‌های تقاضای پیش‌بینی‌شده» هستند، نه احتمال و نه فاصلهٔ اطمینان آماری. به همین علت هیچ‌جا درصد احتمال سودآوری گزارش نمی‌کنیم.

## API

Endpoint جدید:

```text
POST /v1/optimization/comparisons
```

درخواست دو بخش دارد: `optimization` که شامل سناریوهای دارای مدرک و محدودیت‌هاست، و `policy` که آستانهٔ مصوب مدیر را دارد. API حداکثر ۱۰۰ سناریو در هر درخواست می‌پذیرد تا پردازش synchronous سنگین یا نامحدود نشود. اگر ارز سیاست با ارز سناریوها یکی نباشد، درخواست با خطای ۴۲۲ رد می‌شود.

پاسخ برای هر سناریو وضعیت محدودیت‌ها، بازهٔ سود افزایشی، آستانه، طبقه‌بندی و توضیح کوتاه دارد. در سطح کل پاسخ همیشه `selection_status=manual_review_required` و `selected_scenario_id=null` باقی می‌ماند.

نام تأییدکننده و مرجع آستانه در API فقط اطلاعاتی هستند که درخواست‌کننده ثبت می‌کند؛ چون احراز هویت نداریم، سیستم ثابت نمی‌کند آن شخص واقعاً مدیر یا تأییدکننده است.

بودجهٔ کل در این نسخه برای هر سناریو جداگانه غربال می‌شود. هنوز بودجه میان سناریوها تقسیم نمی‌شود؛ بنابراین این API را نباید به‌عنوان بهینه‌ساز سبد بودجه معرفی کرد.

## فایل‌های تغییرکرده

- `src/promoguard/optimization/decision_policy.py`: تعریف آستانهٔ مدیر و چهار طبقه‌بندی تصمیم.
- `src/promoguard/optimization/__init__.py`: خروجی عمومی قراردادها و تابع سیاست.
- `apps/api/contracts.py`: قرارداد API و سقف ۱۰۰ سناریو.
- `apps/api/main.py`: endpoint مقایسهٔ سناریوها.
- `tests/unit/test_optimization_contracts.py`: مرز آستانه، محدودیت، واحد پول و عدم انتخاب خودکار.
- `tests/integration/test_api.py`: آزمون endpoint واقعی.
- `ROADMAP.md`: شواهد مرحله و وضعیت فاز فعال.

## اجرای تست

```powershell
$env:PYTHONPATH='src;.'
python -m pytest tests/unit/test_optimization_contracts.py tests/integration/test_api.py -q
python -m ruff check src/promoguard/optimization apps/api tests/unit/test_optimization_contracts.py tests/integration/test_api.py
python -m compileall -q src apps
python -m pytest -q
```

در پیاده‌سازی این برش، سند انتخاب مدل PromoGuard پیشنهاد `gpt-5.6-sol` با `xhigh` را برای Phase 8 می‌دهد، اما آن مدل در این محیط قابل انتخاب نبود. تغییر provider یا تنظیمات سراسری هم در اختیار این اجرا نیست. این برش با runtime فعلی GPT-6 انجام شد؛ سطح reasoning ابزار در این جلسه به‌صورت قابل‌ثبت نمایش داده نمی‌شد. به همین دلیل پذیرش بر اساس تست و قراردادهای قطعی انجام شده، نه ادعای بازبینی مستقل مدل دیگر.

## محدودیت و سؤال مدیر

این endpoint هنوز به داشبورد وب متصل نیست و آستانه نیز باید واقعاً توسط مدیر مشتری تعیین شود. دادهٔ عمومی پروژه، هزینه و margin شرکت را ثابت نمی‌کند. نتیجهٔ `candidate_for_human_review` نیز صرفاً عبور از آستانه روی فرض‌های ورودی است؛ برای ادعای سود واقعی، تعریف اقتصاد، کیفیت forecast و طراحی آزمایش باید جداگانه بررسی شوند.

**اگر مدیر بپرسد «یعنی سیستم به من می‌گوید اجرا کنم؟»** پاسخ: «نه. سیستم محدودیت‌ها و مقایسه با آستانه‌ای را که خودتان تعیین کرده‌اید نشان می‌دهد. اگر حتی حالت محافظه‌کارانه از آستانه بگذرد، فقط می‌گوید ارزش بررسی انسانی دارد. تأیید نهایی با شماست.»
