# راهنمای صفحهٔ بررسی سناریوهای کمپین

## این بخش چه کاری انجام می‌دهد؟

صفحهٔ `/optimization` یک درخواست اقتصادیِ از پیش آماده‌شده را می‌گیرد، آن را به API محلی PromoGuard می‌فرستد و پاسخ را برای بازبینی مدیر خواناتر می‌کند. ورودی ممکن است فایل JSON باشد یا متن JSON که در کادر صفحه قرار داده می‌شود.

این صفحه خودش از فروش تاریخی شرکت تقاضا را تخمین نمی‌زند و فایل فروش خام را هم به سناریوی اقتصادی تبدیل نمی‌کند. در این مرحله باید سناریو، اعداد اقتصادی، بازهٔ تقاضا و مدارک پشتیبان از قبل آماده باشند. به همین دلیل، صفحه عمداً امکان پرکردن یک فرم کوتاه با اعداد ساختگی را به‌جای دادهٔ مستند جا نمی‌زند.

## مسیر داده از مرورگر تا نتیجه

1. کاربر فایل JSON را انتخاب می‌کند یا متن درخواست را وارد می‌کند.
2. مرورگر فقط بررسی می‌کند که متن، JSON معتبر و یک شیء باشد.
3. درخواست به `POST /v1/optimization/comparisons` در API محلی ارسال می‌شود.
4. API قرارداد Pydantic و شواهد لازم برای ورودی‌های مالی را اعتبارسنجی می‌کند، محدودیت‌های هر سناریو را می‌سنجد و اقتصاد شرطی را محاسبه می‌کند.
5. صفحه برای هر سناریو بازهٔ سود افزوده، وضعیت نسبت به آستانهٔ مدیر، موانع و توضیح را نشان می‌دهد.

فرمول یا منطق تحلیلی در فرانت‌اند کپی نشده است؛ فرانت‌اند صرفاً ورودی می‌فرستد و پاسخ تایپ‌شدهٔ API را نمایش می‌دهد. اگر پاسخ API به شکل انسانی و واضح منتشر نشود، صفحه نتیجه‌ای را اختراع نمی‌کند.

## داده‌های لازم

در هر سناریو باید شناسهٔ فروشگاه و کالا، بازهٔ تاریخ، ارز، قیمت عادی و کمپین، بهای واحد، حمایت تأمین‌کننده، هزینهٔ ثابت و متغیر، موجودی، تقاضای مبنا و بازهٔ تقاضای کمپین موجود باشد. برای هر یک از ۹ ورودی اقتصادی، قرارداد داده یک رکورد شواهد می‌خواهد: نام فیلد، نوع منبع، مرجع، تاریخ و نام ثبت‌شدهٔ تأییدکننده.

دکمهٔ «دریافت قالب خالی» شکل کامل JSON را دانلود می‌کند. مقدارهای خالی و `null` عمداً دادهٔ نمونه نیستند و API آن قالب را تا زمان تکمیل با دادهٔ مستند نمی‌پذیرد.

در سطح درخواست نیز بودجهٔ کل، حداقل سهم هر واحد، حداکثر نرخ تخفیف، ذخیرهٔ موجودی و الزام تأیید انسانی لازم است. سیاست مدیر حداقل سود افزوده، ارز، مرجع تصمیم، نام تأییدکننده و تاریخ را ثبت می‌کند.

## معنی وضعیت‌ها

- «رد شده در بررسی محدودیت‌ها»: دست‌کم یکی از شروط ورودی رد شده است؛ این پیام به‌تنهایی نمی‌گوید کمپین در دنیای واقعی بد است.
- «نامزد بررسی مدیر»: حتی کران پایینِ بازهٔ تقاضای واردشده به حداقل هدف می‌رسد؛ این تأیید اجرا نیست.
- «پایین‌تر از حداقل هدف مدیر»: حتی کران بالای بازه به حد نمی‌رسد؛ این دستور توقف خودکار نیست.
- «برای قضاوت کافی نیست»: بازه از آستانه عبور می‌کند و با اطلاعات فعلی نمی‌توان سمت تصمیم را روشن کرد.

## چه چیزهایی هنوز انجام نمی‌شود؟

- ورودی‌های مالی یا مرجع مدارک به‌طور مستقل با سیستم شرکت تطبیق داده نمی‌شوند.
- نام تأییدکننده فقط متن است و هویت فرد احراز نمی‌شود.
- بازهٔ تقاضا بازهٔ سناریویی است، نه فاصلهٔ اطمینان آماری و نه اثر علّی پروموشن.
- بودجه برای هر گزینه جداگانه غربال می‌شود؛ تقسیم بودجه بین چند کمپین یا بهینه‌سازی سبد نداریم.
- سیستم سناریوها را رتبه‌بندی یا انتخاب نمی‌کند و کمپینی را اجرا نمی‌کند.
- این صفحه گزارش پایدار با Report ID نمی‌سازد و درخواست را در مرورگر یا سرور ذخیره نمی‌کند.
- صفحه برای دادهٔ محرمانه مناسب نیست، مگر آن‌که محیط اجرا، دسترسی و سیاست نگهداری سازمان مجاز و کنترل‌شده باشد.

## اجرای محلی

در یک ترمینال از ریشهٔ مخزن، API را اجرا کن:

```powershell
$env:PYTHONPATH = "src"
python -m uvicorn apps.api.main:app --host 127.0.0.1 --port 8000
```

در ترمینال دوم:

```powershell
cd frontend
npm run dev
```

سپس `http://127.0.0.1:3000/optimization` را باز کن. این آدرس فقط برای اجرای محلی است.

## بررسی کیفیت این برش

- `npm run typecheck` — پاس.
- `npm run build` — پاس؛ مسیر `/optimization` به صورت صفحهٔ ایستا در Build تولید شد.
- GET محلی `/optimization` — پاسخ ۲۰۰ و تیتر صفحه در HTML دیده شد.
- API `/health` — پاسخ ۲۰۰.
- تست‌های سمت API و دامنه در اجرای قبلی این برش: ۲۳۹ پاس.

در تست مرورگر صفحه صرفاً بارگذاری شد؛ یک دور دستی کامل شامل انتخاب فایل واقعی مجاز، ارسال به API و بازبینی نتیجهٔ مدیر هنوز انجام نشده، چون ورودی اقتصادی واقعیِ تأییدشده در دسترس نیست.

## تکمیل بعدی: نمایش ریز محاسبه

پاسخ هر سناریو اکنون علاوه بر سود افزوده، سود حالت عادی، بازهٔ سود کمپین، سه حالت تقاضای واردشده، نرخ تخفیف، سهم محاسباتی هر واحد پس از هزینهٔ متغیر، هزینهٔ معاملاتی و موجودی قابل فروش را هم حمل می‌کند. صفحه این موارد را در جزئیات بازشونده نشان می‌دهد تا مخاطب بتواند عدد اصلی را به اجزای قابل فهم بشکند.

در این تغییر هیچ فرمولی دوباره در رابط نوشته نشده است. دادهٔ جزئی از همان `ScenarioFeasibility` و `ConditionalEconomics` محاسبه‌شده در هسته می‌آید. تست واحد و API مقادیر مورد انتظار یک ورودی ثابت را بررسی می‌کنند؛ آن ورودی فقط fixture آزمایشی است و دادهٔ مشتری یا نتیجهٔ بازار نیست. نمایش breakdown هم صحت سندهای ورودی را ثابت نمی‌کند.

### نتیجهٔ بازبینی نهایی این برش

- تست متمرکز بهینه‌سازی و API: ۴۱ پاس.
- کل تست‌های Python: ۲۴۰ پاس؛ فقط یک هشدار قدیمی وابستگی Starlette/httpx باقی ماند.
- Ruff روی فایل‌های Python تغییرکرده، `compileall`, `npm run typecheck`, `npm run build` و `git diff --check`: پاس.
- نسخهٔ تولیدی محلی: صفحهٔ `/optimization`، فایل قالب و درخواست CORS مرورگر هرکدام پاسخ HTTP 200 دادند.
- محاسبهٔ انتهابه‌انتها با دادهٔ شرکت انجام نشده؛ ورودی اقتصادی واقعی و مجاز در اختیار نیست.

این تغییر صرفاً پاسخ محاسبهٔ قبلی را شفاف‌تر می‌کند. runtime این جلسه امکان انتخاب مدل و سطح reasoning را برای ثبت گزارش نشان نداد؛ چون روش آماری یا آستانهٔ تصمیم تغییر نکرد، این کار را بازبینی آماری مستقل نمی‌دانیم.

## اصلاح‌های بازبینی بعدی

در بازبینی رابط، سه ایراد کاربردی پیدا شد و اصلاح شد:

1. بعد از ویرایش ورودی، نتیجهٔ قبلی پاک می‌شود؛ هنگام خواندن فایل یا فرستادن درخواست، ویرایش و انتخاب فایل قفل است. شمارهٔ نسخهٔ ورودی هم کنترل می‌شود تا پاسخ قدیمی به ورودی تازه نسبت داده نشود.
2. صفحه برای بررسی JSON از `JSON.parse` استفاده می‌کند، اما همان متن اصلی را برای API می‌فرستد. بنابراین عددی مثل `9007199254740993` هنگام بازسازی درخواست به عدد دیگری تبدیل نمی‌شود. برای نمایش پاسخ هم قالب‌ساز رشتهٔ اعشاری از `Number` استفاده نمی‌کند و گردکردن تا دو رقم را با `BigInt` انجام می‌دهد.
3. لینک‌های «آمادگی داده» و «ممیزی پروموشن» به ترتیب با `?section=readiness` و `?section=promotion` به صفحهٔ اصلی می‌روند؛ صفحه این بخش را از URL می‌خواند و پس از آماده‌شدن داده نگه می‌دارد.

هزینهٔ معاملاتی در رابط به‌صراحت «بر پایهٔ تقاضای بالای برآوردی» نام‌گذاری شده است؛ این عدد برای غربال بودجهٔ محافظه‌کارانه است و هزینهٔ قطعی فروش واقعی نیست.

تست‌های قالب‌سازی در `frontend/app/optimization/format.test.mjs` اعداد بزرگ‌تر از محدودهٔ امن جاوااسکریپت، نماد علمی، جابه‌جایی اعشار برای درصد، گردکردن و منفی صفر را می‌سنجند. تست رابط مرورگر به‌صورت خودکار وجود ندارد؛ typecheck و build کنترل می‌کنند که صفحه و مسیرها همچنان درست کامپایل شوند.

### نمایش خطاهای قرارداد به زبان روشن

اگر API درخواست را رد کند، ممکن است چند خطای ساختاری و مقداری را هم‌زمان پس بفرستد. صفحه اکنون مسیر هر خطا را به نام‌های قابل‌خواندن فارسی تبدیل می‌کند؛ مثلاً `policy → minimum_incremental_profit` را به «سیاست حداقل سود ← حداقل سود افزوده» تبدیل می‌کند. خطای تاریخ یا عدد هم پیام راهنمای کوتاه دارد. در پاسخ‌هایی با خطاهای زیاد، هشت مورد اول نشان داده می‌شوند و تعداد باقی‌مانده هم اعلام می‌شود.

تبدیل متن خطا در `frontend/app/optimization/api-errors.mjs` است و در `api-errors.test.mjs` برای مسیر فیلد، شمارهٔ سناریو، تاریخ نامعتبر، تعداد زیاد و خطای ناشناخته تست دارد. این تغییر پیام API را برای کاربر روشن می‌کند؛ اعتبارسنجی اصلی همچنان در قرارداد Pydantic سمت سرور انجام می‌شود.
