# راهنمای مرحلهٔ ۸.۲.۷: فرم مرحله‌ای ورود سناریوی کمپین

## هدف به زبان ساده

تا پیش از این، برای مقایسهٔ سناریوها باید یک درخواست JSON طولانی را دستی می‌ساختی. این کار هم خطاپذیر بود و هم برای مدیر فروش مناسب نبود. حالا فرم سه‌مرحله‌ای اطلاعات لازم را می‌گیرد، مدرک هر عدد را ثبت می‌کند و در پایان JSON سازگار با قرارداد فعلی می‌سازد. این JSON هنوز باید با دکمهٔ «مقایسهٔ سناریوها» جداگانه برای API فرستاده شود؛ ساختن فرم به‌تنهایی تحلیل را اجرا نمی‌کند.

## سه مرحله چه می‌گیرند؟

1. **مشخصات و محدودیت‌ها:** شناسهٔ درخواست و سناریو، کالا و فروشگاه، تاریخ کمپین، واحد پول، سقف هزینه، حداقل سهم هر واحد، سقف تخفیف و ذخیرهٔ موجودی.
2. **اعداد سناریو:** قیمت عادی و کمپین، بهای تمام‌شده، حمایت تأمین‌کننده، هزینه‌های ثابت و متغیر، موجودی، تقاضای مبنا و سه مقدار تقاضای پایین/میانی/بالا.
3. **مدرک و آستانهٔ مدیر:** برای هر یک از ۹ ورودی اقتصادی نوع مدرک، مرجع، تاریخ و تأییدکننده ثبت می‌شود؛ سپس حداقل سود افزودهٔ مورد قبول و مرجع تأیید مدیریتی دریافت می‌شود.

هیچ عددی از قبل پر نشده است. عدد صفر هم نباید برای «نداریم» استفاده شود؛ فقط وقتی مسئول داده تأیید کرد مقدار واقعاً صفر است، آن را صفر ثبت کن و مدرکش را بنویس.

## معماری

- `ScenarioRequestBuilder.tsx` فقط فرم و گام‌های رابط کاربری را مدیریت می‌کند.
- `request-builder.mjs` دادهٔ فرم را کنترل و به ساختار ورودی API تبدیل می‌کند.
- `request-builder.test.mjs` منطق تبدیل و خطاهای کلیدی را بدون نیاز به سرویس بیرونی آزمایش می‌کند.
- `page.tsx` JSON تولیدشده را در مسیر فعلی قرار می‌دهد. کاربر آن را بازبینی می‌کند و با کلیک خودش اجرا می‌کند.
- API همچنان مرجع نهایی اعتبارسنجی است؛ ترتیب تاریخ‌ها، سازگاری واحد پول، بازهٔ تقاضا و قیود مالی سمت سرور کنترل می‌شوند.

## دقت اعداد و کنترل‌های مهم

- اعداد اعشاری به شکل متن دقیق داخل JSON نگه داشته می‌شوند؛ آن‌ها را به عدد JavaScript تبدیل نمی‌کنیم، چون ممکن است رقم‌های پایانی گرد شوند.
- تعداد موجودی و ذخیرهٔ موجودی باید عدد صحیح و در محدودهٔ امن مرورگر باشند.
- تاریخ به قالب میلادی `YYYY-MM-DD` نیاز دارد. تاریخ شمسی مثل `1405/07/10` را مستقیم وارد نکن؛ ابتدا آن را به تاریخ میلادی درست تبدیل کن.
- واحد پول باید کد سه‌حرفی باشد. واحد پول درخواست، سناریو و آستانه باید یکی باشند.
- تمام ۹ مورد مدرک الزامی‌اند؛ حتی اگر مقدار یک هزینه صفر است، مدرک/تأیید آن صفر لازم است.
- تأییدکننده و مرجع در این مرحله فقط متن‌اند؛ سیستم هویت افراد یا اصالت فایل را تأیید نمی‌کند.
- `human_approval_required` همیشه درست و `automatic_execution_allowed` همیشه نادرست است.
- فرم فقط یک سناریو می‌سازد. برای چند سناریو یا قرارداد کامل‌تر می‌توان از مسیر JSON پیشرفته استفاده کرد.

## فایل‌هایی که در این مرحله تغییر کردند

- `frontend/app/optimization/ScenarioRequestBuilder.tsx`: فرم فارسی سه‌مرحله‌ای، فیلدها، خطاهای قابل‌فهم و اتصال به مسیر JSON.
- `frontend/app/optimization/request-builder.mjs`: اعتبارسنجی اولیه و ساخت درخواست بدون جعل مقدار.
- `frontend/app/optimization/request-builder.d.mts`: تعریف نوع برای استفادهٔ امن helper در TypeScript.
- `frontend/app/optimization/request-builder.test.mjs`: آزمون فرم خالی، ساخت JSON، دقت اعشار، مدارک، تاریخ، واحد پول و عدد صحیح.
- `frontend/app/optimization/page.tsx`: انتخاب فرم راهنما یا ورود فایل/JSON؛ JSON ساخته‌شده اجرا نمی‌شود تا کاربر خودش آن را بازبینی و ارسال کند.
- `frontend/app/optimization/optimization.module.css`: اجزای بصری فرم و نمایش مناسب در صفحهٔ کوچک.
- `frontend/package.json`: اضافه‌شدن تست‌های سازنده به فرمان تست موجود.
- `ROADMAP.md`: ثبت دامنه، محدودیت و دروازهٔ واقعی باقی‌مانده.

## فرمان‌ها و نتیجهٔ آزمون

- `npm run test:format` در `frontend`: **۹ تست پاس شد**.
- `npm run typecheck` در `frontend`: پاس شد.
- `npm run build` در `frontend`: ساخت تولیدی Next.js پاس شد.
- `python -m pytest tests/unit/test_optimization_contracts.py tests/integration/test_api.py -q`: **۴۱ تست پاس شد**؛ یک هشدار deprecation موجود در Starlette/httpx باقی است.
- `git diff --check`: پاس شد.

## مواردی که این مرحله ثابت نمی‌کند

این UI اثبات نمی‌کند اعداد واقعی یا سودآورند، سند مجاز است، تأییدکننده واقعاً صاحب اختیار است یا کمپین باید اجرا شود. این مرحله دادهٔ شرکت یا نتیجهٔ تجاری جدید اضافه نمی‌کند و روش محاسبهٔ سود را تغییر نمی‌دهد. در نهایت هنوز فایل مجاز شرکت و بازبینی مدیر فروش لازم است.

## پرسش‌های احتمالی در جلسهٔ فنی

**چرا JSON را حذف نکردیم؟** مسیر JSON برای تحلیل‌گر یا بارگذاری خروجی سیستم‌های دیگر مفید است؛ فرم فقط گزینهٔ ساده‌تر را اضافه می‌کند.

**چرا برای بعضی فیلدها «صفر» را خودکار نمی‌گذاریم؟** چون صفر یک ادعای واقعی دربارهٔ هزینه یا حمایت است. باید از منبع داده تأیید شود؛ خالی‌گذاشتن امن‌تر از فرض‌کردن است.

**چرا مبلغ‌ها رشته‌اند ولی موجودی عدد است؟** برای نگه‌داشتن دقیق رقم‌های مبلغی، رشتهٔ اعشاری به API فرستاده می‌شود. شمارش موجودی باید عدد صحیح باشد و از حد دقت امن مرورگر بیشتر نشود.

**آیا فرم به شرکت اجازهٔ اجرای کمپین می‌دهد؟** خیر. فقط درخواست بررسی می‌سازد؛ پاسخ API هم تصمیم را برای بازبینی انسانی نگه می‌دارد و اجرای خودکار خاموش است.

## توضیح یک‌دقیقه‌ای

«این مرحله برای این بود که مدیر مجبور نباشد JSON فنی بنویسد. فرم را از مشخصات کمپین شروع می‌کنیم، بعد اعداد و پیش‌بینی‌های تأییدشده را می‌گیریم، سپس منبع تک‌تک ۹ عدد و حداقل هدف مدیر را ثبت می‌کنیم. فرم فقط درخواست را می‌سازد؛ خودم قبل از ارسال می‌توانم JSON را ببینم. تا وقتی داده و مدرک مجاز نباشد، نتیجه را نباید واقعی یا قطعی جا زد.»
